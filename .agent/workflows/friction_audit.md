# /friction_audit: エージェント開発フリクション監査

このワークフローは、人間とAIエージェントの間の共同作業において発生する「概念的な摩擦（Friction）」を特定し、プロジェクトの「Source of Truth」を再調整するためのものである。

## 手順

### 1. 症状のサンプリング
最近のログやタスク履歴から、以下の「フリクションの兆候」を特定せよ。

### 2. タスクアサーションの宣言 (ATC)
特定された症状を分析し、作業のベースラインを固定するため、[Axiomatic Task Contract](/docs/patterns/axiomatic_task_contract.md) を宣言せよ。
- 初期状態（@pre）には、現在発生しているフリクションの状態を記述すること。

### 3. 三層の矛盾チェック
以下のフリクション兆候をサンプリングし、3つの要素が整合しているか分析せよ。
- **Tool Failure**: WIT parserエラーやコンパイルエラーなど、ツールの厳しい制約に衝突したケース。
- **Conceptual Drift**: ユーザーの意図と、生成された設計（例：Harnessのポリモーフィズム）の間に乖離があったケース。
- **Context Noise**: MEMORY内の古い定義が、最新のタスクの邪魔をしたケース。

1. **仕様ドメイン (Natural Language Specs)**
   - `docs/` 内の仕様書が、最新の設計判断（例：ConceptベースDI）を反映しているか。
   - 言葉の定義（型語彙）が曖昧で、エージェントが勝手な解釈をしていないか。

2. **プロセスドメイン (Workflows)**
   - 実行しているワークフローの指示が、現在のプロジェクトの複雑度（Risk Tier）に対して適切か。
   - ワークフローの記述が「何をすべきか」ではなく「どう書くか（実装詳細）」に寄りすぎていないか。

3. **コンテキストドメイン (Prompts / Memory)**
   - MEMORYタグで提供されている情報が、最新のWIT定義と矛盾していないか。
   - プロンプトの優先順位（User rules vs Task summary）が機能しているか。

### 4. フリクション解消アクション (Triaging)
特定されたフリクションに対し、以下のいずれかのアクションを取れ。

- **A. 仕様書の同期**: 議論の結果を `docs/` または `MEMORY` に即座に反映し、エージェントの「知識の基盤」を更新する。
- **B. ワークフローのリファインメント**: 指示内容をより抽象化するか、あるいはより厳密なチェックリストに変更する。
- **C. コンテキストの整理**: 古くなった `task.md` や `implementation_plan.md` を整理し、ノイズを排除する。
- **D. ツール/自動生成の修正**: WITジェネレータなどの不備を修正し、機械的なフリクションを排除する。

## 出力
監査結果を `walkthrough.md` または独立した報告ドキュメントとして提示し、ユーザーに「どの摩擦を取り除くべきか」を提案すること。
