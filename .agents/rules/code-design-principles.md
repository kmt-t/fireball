# コード設計の原則

実装とレビューで確認する、コードの設計原則を定める。
特定の言語、ライブラリ、プロジェクトの構造に依存しない。
言語ごとの規約は `coding-standards-*.md`、失敗の扱いは [開発方針](development-policy.md)の `Contract-First / Fail-Fast` を正本とする。

## 1. 位置づけ

- 原則は、規則の網羅ではなく、判断の軸である。
- 個別の書き方を増やさず、原則に照らして理由を説明する。
- 速さと読みやすさは、同じ原則から得る。手本となる実装がある場合は、先にその実装を読む。

## 2. 原則

### 2.1 確定した情報を再判定しない

- 一度確定した値、状態、契約を、下流で再び分岐して確かめない。
- 確定する場所を一つに決め、以降の経路はその結果だけを前提にする。
- 契約違反の扱いは `Contract-First / Fail-Fast` に従う。

例: 呼び出し側が条件を判定した後で、呼ばれた側が同じ条件を再び分岐する。

### 2.2 分岐で分かったことを、値に書いて読み直さない

- 分岐した場所で、その分岐に固有の処理を行う。
- 分岐の結果を種別として保存し、後段で読み直して再び分岐する形にしない。
- 後段で複数の経路を一つに合流させる必要があるときだけ、種別を持つ。

例: 理由を表す値を変数に書き、別の場所でその値により分岐して処理を選ぶ。

### 2.3 事前に確定できる値を、実行時に分岐しない

- 構築時、読み込み時、コンパイル時に確定する値は、その時点で確定する。
- 実行時の分岐は、実行時にしか決まらない値に限る。
- 確定済みの構成の違いは、型、テンプレート、事前に選んだ表で表す。

例: 起動後に変わらない設定を、毎回の処理で条件分岐して読む。

### 2.4 状態の所有者を一つにする

- 同じ状態を、複数の場所で読み書きしない。
- 状態を更新する手続きは一つにまとめ、他は結果を読むだけにする。
- 同じ値の写しを持つ場合は、写しを持つ理由と更新の責任者を明示する。

例: 同じフラグを、呼び出し元と呼び出し先の双方が別々に設定し、解除する。

### 2.5 同じ責務の経路を重複させない

- 役割が同じ経路が複数ある場合は、一つに統合する。
- 統合すると動作が変わる場合は、変わる動作を明示して判断を仰ぐ。
- 経路の違いが仕様に由来しないなら、違いを残さない。

例: 名前の違う二つの経路が、ほぼ同じ前処理と後処理を別々に持つ。

## 3. 適用

- 実装前に、対象の経路が各原則に反していないかを確認する。
- レビューでは、反する箇所をコードの行で示し、原則の番号で理由を説明する。
- 原則に反する箇所を残す場合は、理由を実装またはレビューの記録に書く。
- 原則を追加するときは、複数のプロジェクトで通用するか確認する。特定の構造にだけ通用する指摘は、原則に加えない。
