# Fireball 仕様書・ドキュメント標準 (Documentation Standards)

本ドキュメントは、Fireball プロジェクトにおける要求仕様書・アーキテクチャ設計書・コンポーネント設計書の記述形式、構造、および図解の規約を定義する。
文書階層、メタキーワード、traceability の正本は `docs/architecture/document_structure.md` とする。

## 1. 基本原則 (Core Principles)

- **自然言語（日本語）仕様の徹底**:
  - ドキュメント本文、見出し、表の項目名はすべて自然言語（日本語）で記述する。
  - 設計が特定の実装詳細（C++ の内部クラス名・型名、Python の `bytearray` 等）や一時的な内部データ構造用語（`(AoS)` 等）に依存してはならず、目的・意図・課題を解消するコンセプトおよび不変条件を自然言語で記述する。
  - コード名、API シンボル名、メタキーワード、URI のみ英語を用いる。
  - WebAssembly、AAPCS、C++標準などの外部標準・正式仕様で定義された用語、命令名、構造名は、仕様の正式名称をそのまま記載する。正式仕様にない独自の翻訳語、略称、実装由来の別名を作ってはならない。例として、WebAssemblyの `block`、`loop`、`if`、`br`、`br_if`、`end` は原表記を維持する。
  - 外部仕様の正式名称とFireball内部の実装用語を混同してはならない。外部仕様の語は仕様上の意味として記載し、内部の格納形式・管理領域・補助データ構造は日本語の概念として記載する。
- **静的設計と動的設計のセット定義 (Bonsai Design Step 0)**:
  - コンポーネント設計書は、静的構造と動的振る舞いを必ずペアで定義する。
  - **静的設計**: データ構造定義、メモリレイアウト、主要クラス・構造体・定数、内部ブロック図（`graph TD`）。
  - **動的設計**: 状態遷移図（`stateDiagram-v2`）、アルゴリズム、相互作用。
- **動的アルゴリズム可視化の厳格な使い分け**:
  - **責務が重要な場合 $\implies$ シーケンス図 (`sequenceDiagram`)**:
    - 複数の独立したタスク、アクター、コンポーネント間でのメッセージ送受信、制御委譲、リソース所有権の遷移（Revoke $\to$ Rendezvous $\to$ Grant 等）。
  - **手順が重要な場合 $\implies$ アクティビティ図 (`flowchart TD`)**:
    - 単一コンポーネント内部における条件分岐、事前検証、ロールバック、多段パイプライン等の決定論的手順。
- **例示コード・擬似コードの整合性と鮮度**:
  - ドキュメント内に記載される例示コード・擬似コード・API使用例は、本文の解説、表定義、およびリファレンス実装（コンセプトコードやWIT定義）と厳密に整合していなければならない。
  - 本文やAPI定義を改定した際に例示コードの更新が漏れ、過去の旧仕様・廃止された引数や型が残存する「例示コードの陳腐化」を徹底排除する。

- **本文の可読性と一文一義・情報分解**:
  - **一文一義の原則**: 1つの文（句点「。」で区切られる単位）で述べる命題・事実・契約は原則1つとする。1つの文に前提・動機・不変条件・例外・検証エビデンスを混在させない。
  - **長大複文の排除と文長目安**: 「〜であり、〜のため、〜によって、〜となるが、〜」のように接続助詞で節を数珠繋ぎにしない。文長の目安は60〜80文字とし、最大でも100文字以内で句点を打つ。
  - **主述の近接**: 主語の直後に長大な修飾節や入れ子の括弧書きを挟み込まず、主語と述語の距離を近づけて結論を先に見せる。補足が長い場合は後続文または箇条書きとして独立させる。
  - **契約（本筋）と理由・検証の分離**: 仕様としての不変条件・動作契約をまず短文で確定・断定し、理由（Why）や裏付けとなる検証エビデンスは次の文または箇条書きとして分離する。
  - **本筋先行と箇条書き分解**: 手順と注意事項はそれぞれ簡潔な箇条書きに分ける。手順と付帯条件を同じ段落で説明する場合は、先に本筋を短く示し、その後に付帯条件を目的別の箇条書きへ分ける。
  - **付帯条件の優先順位**: 付帯条件は、適用範囲・安全性・正確性・性能・実装上の補足の順を基本とし、影響が大きいものから並べる。文書固有のリスクがある場合は、その重要度順を優先する。
  - **段落の情報過多禁止**: 一つの段落に、手順、前提条件、例外、制約、理由、検証方法を詰め込まない。各情報は本筋または適切な付帯条件グループへ配置する。
  - **段落の役割と構成の型**: 段落の境界は文の長さや句点だけで決めず、説明の役割が切り替わる位置に置く。同じ役割に属する関連文は一段落にまとめてよい。次の型は代表例であり、すべてを一節に使う必要はない。
    - **定義・契約型**: 対象と責務を示し、保証する動作・不変条件を述べる。適用条件や例外は必要な場合に続けて分ける。
      - 例: 「XはYを担う。Xは条件Zで動作Aを保証する。」
    - **動作・手順型**: 前提または契機、実行する処理、結果または失敗時の動作を順に示す。
      - 例: 「条件Aで処理を開始する。Xは手順Bを実行する。成功時はCへ遷移し、失敗時はDを返す。」
    - **理由・設計判断型**: 解決する問題またはリスク、採用する方針、その効果や根拠を分けて示す。
      - 例: 「課題Aを避けるため、方針Bを採用する。この方針によりCを保証する。根拠は検証Dで確認する。」
    - **検証型**: 前提条件、操作、観測可能な期待結果を対応付ける。設計理由は期待結果と混ぜず、別の説明段落に置く。
      - 例: 「前提はAである。操作Bを行う。結果Cになることを確認する。」
    - 段落を分ける際は、要求、条件、制約、例外、理由、証拠の役割を見極める。型に合わせるために情報を削除したり、同じ内容を重複させたりしてはならない。
  - **情報欠落の防止**: 箇条書きへ分解する前後で、要求、前提条件、制約、例外、理由、検証方法が欠落していないことを照合する。可読性の改善を理由に情報を削除してはならない。
  - **文体統一と過去経緯排除**: 文末はすべて常体（だ・である調／体言止め）で統一し、敬体（です・ます）や曖昧な推量表現（〜と思われる等）を排除する。理由や根拠の説明は許可するが、過去の経緯、作業履歴、変更前の状態は本文へ持ち込まない。必要な判断根拠は現在の仕様上の理由として簡潔に記述する。
  - **カタカナ用語統制（JIS Z 8301 準拠）**: 3音以上のカタカナ専門用語の末尾長音記号は省略形（`スケジューラ`、`インタープリタ`、`アロケータ`、`ドライバ`、`マネージャ`、`ルータ`、`レジスタ`、`パラメータ`、`メモリ`等）に統一する（`ユーザー` 等の一般名詞は除く）。

## 2. トレーサビリティとメタキーワード (`{Keyword}`)

- **メタキーワード台帳との連携**:
  - すべての仕様、設計、テスト、形式検証モデルは `docs/architecture/keyword_dictionary.md` に登録された統一アンカー `{Keyword}` で相互にリンクする。
  - 壊れやすいファイル名や章番号による参照を禁止し、キーワードによる単一の真実（Single Source of Truth）を維持する。
- **キーワードの記法規約（定義＝インライン、参照＝コメント）**:
  - **定義はインライン記述**: キーワードの定義元（Source of Truth）となる箇所では、本文中や表（要求仕様テーブル、台帳等）にインラインで `{Keyword}` を直接記述する。
  - **参照はコメント記述**: 他の文書やセクションから当該キーワードを参照・追跡する場合は、セクション見出し直下の HTML コメント `<!-- traceability: {Keyword1} {Keyword2} -->` に記述する。
  - **本文中のダミー参照行の禁止**: 本文中に参照目的のキーワード列（例: `関連キーワード: {...}`）をインライン記述してはならない。参照は必ず `<!-- traceability: ... -->` コメント内に記述する。
- **検証エビデンス明示タグ**:
  - 各設計書のタイトル直下には `<!-- evidence: ... -->` を付与し、裏付けとなる検証手段（`formal`, `benchmark`, `wit`, `concept`）を明記する。
- **キーワードとテストケースIDの区別**:
  - `{Keyword}` は意味を持つトレーサビリティアンカーとし、「接頭辞＋数字」だけのキーワードを新設しない。
  - `TEST-<コンポーネント>-<テスト番号>`（例: `TEST-INT-01`、`TEST-MEM-14`、`TEST-JITR-26`）はテストケースIDであり、キーワードではない。テスト仕様書・台帳では「テストケースID」と明記して紐づける。
  - `BENCHMARK-<コンポーネント>-<ID>`（例: `BENCHMARK-MEM-01`、`BENCHMARK-VMMIO-01`）はベンチマークIDであり、テストケースID・キーワードとは区別する。
  - `GOTCHA-<COMPONENT>-<連番>` は、設計理由と対応テストを持つ GOTCHA 固有IDに限り許可する。
  - 純粋な文書間リンクにだけ `LINK-<連番>` を使い、要求・ADR・Challenge・コンポーネント仕様の意味キーワードを連番へ置換しない。
- **直交表による網羅性検討**:
  - 公開 API の各パラメータ、エラー種別、内部状態の組み合わせについて、直交表（Pairwise / All-Pairs）を用いて網羅性を検討・記録する。

## 3. Mermaid 記法規約

- **特殊記号のクォート**:
  - ノードラベル内に括弧 `()` や角括弧 `[]`、特殊記号が含まれる場合は、構文エラーを防ぐため必ず二重引用符で囲む（例: `id["Label (Info)"]`）。
- **ステートマシン (`stateDiagram-v2`)**:
  - 複合状態の入出力遷移、自己ループ、終了状態（`[*]`）を明確に定義する。
- **シーケンス図 (`sequenceDiagram`)**:
  - `autonumber` を付与し、参加者（`actor`, `participant`）の責務分離と活性化区間を正しく対応付ける。
- **フローチャート (`flowchart TD`)**:
  - 開始・終了端子（`(["..."])`）、処理ステップ（`["..."]`）、条件判定（`{"...?"}`）の形状を使い分ける。

## 4. ドキュメント検証チェックリスト

ドキュメント作成・編集完了前に、以下の項目を確認すること：
1. [ ] コンポーネントの責務と境界が明確に定義されているか
2. [ ] 見出しや表の項目名に C++ や Python の内部型名・実装用語が混入せず、自然言語（日本語）で書かれているか
3. [ ] 外部標準・正式仕様の用語を独自の翻訳語や実装由来の別名へ置き換えていないか
4. [ ] 静的内部ブロック図と動的図（シーケンス図／アクティビティ図／状態遷移図）がセットで定義されているか
5. [ ] 複雑な動的アルゴリズムに対し、責務重視＝シーケンス図、手順重視＝アクティビティ図が適切に配置されているか
6. [ ] 図（Mermaid 図）内のノード、状態名、手順、メッセージが本文の解説・表定義と完全一致し、本文改定に伴う図の更新漏れ（図の陳腐化）がないか
7. [ ] ドキュメント中の例示コード・擬似コードが本文の解説・表定義・API定義と完全一致し、本文改定に伴う例示コードの更新漏れ（例示コードの陳腐化）がないか
8. [ ] 上位要求とのトレーサビリティ `{Keyword}` が維持されているか
9. [ ] ドキュメント整合性パイプライン（`spec-consistency.lock` / DocGraph）と整合しているか
10. [ ] 1文で述べる命題が1つに絞られ、一文一義（目安60〜80文字、最大100文字以内）で書かれ、接続助詞による長大複文が排除されているか
11. [ ] 主語の直後に長大な修飾節や入れ子括弧が挟まれず、主語と述語が近接しているか
12. [ ] 段落ごとの役割が明確で、定義・契約、動作・手順、理由・設計判断、検証の情報が不必要に混在していないか。手順と注意事項は分離されているか
13. [ ] 付帯条件が重要度順に並び、要求・前提・制約・例外・理由・検証方法が分解前から欠落していないか
14. [ ] 理由は現在の仕様上の根拠として記述され、過去の経緯や作業履歴を本文へ持ち込んでいないか
15. [ ] 文末が常体（だ・である／体言止め）で統一され、敬体（です・ます）や曖昧な推量表現がなく、カタカナ専門用語の末尾長音省略が徹底されているか
