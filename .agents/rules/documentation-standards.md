# Fireball 仕様書・ドキュメント標準 (Documentation Standards)

本ドキュメントは、Fireball プロジェクトにおける要求仕様書・アーキテクチャ設計書・コンポーネント設計書の記述形式、構造、および図解の規約を定義する。
文書階層、メタキーワード、traceability の正本は `docs/architecture/document_structure.md` とする。

## 1. 基本原則 (Core Principles)

- **自然言語（日本語）仕様の徹底**:
  - ドキュメント本文、見出し、表の項目名はすべて自然言語（日本語）で記述する。
  - 設計が特定の実装詳細（C++ の内部クラス名・型名、Python の `bytearray` 等）や一時的な内部データ構造用語（`(AoS)` 等）に依存してはならず、目的・意図・課題を解消するコンセプトおよび不変条件を自然言語で記述する。
  - コード名、API シンボル名、メタキーワード、URI のみ英語を用いる。
- **静的設計と動的設計のセット定義 (Bonsai Design Step 0)**:
  - コンポーネント設計書は、静的構造と動的振る舞いを必ずペアで定義する。
  - **静的設計**: データ構造定義、メモリレイアウト、主要クラス・構造体・定数、内部ブロック図（`graph TD`）。
  - **動的設計**: 状態遷移図（`stateDiagram-v2`）、アルゴリズム、相互作用。
- **動的アルゴリズム可視化の厳格な使い分け**:
  - **責務が重要な場合 $\implies$ シーケンス図 (`sequenceDiagram`)**:
    - 複数の独立したタスク、アクター、コンポーネント間でのメッセージ送受信、制御委譲、リソース所有権の遷移（Revoke $	o$ Rendezvous $	o$ Grant 等）。
  - **手順が重要な場合 $\implies$ アクティビティ図 (`flowchart TD`)**:
    - 単一コンポーネント内部における条件分岐、事前検証、ロールバック、多段パイプライン等の決定論的手順。

## 2. トレーサビリティとメタキーワード (`{Keyword}`)

- **メタキーワード台帳との連携**:
  - すべての仕様、設計、テスト、形式検証モデルは `docs/architecture/keyword_dictionary.md` に登録された統一アンカー `{Keyword}` で相互にリンクする。
  - 壊れやすいファイル名や章番号による参照を禁止し、キーワードによる単一の真実（Single Source of Truth）を維持する。
- **検証エビデンス明示タグ**:
  - 各設計書のタイトル直下には `<!-- evidence: ... -->` を付与し、裏付けとなる検証手段（`formal`, `benchmark`, `wit`, `concept`）を明記する。
- **トレーサビリティコメント**:
  - セクション見出しの直下には `<!-- traceability: {Keyword1} {Keyword2} -->` を配置し、要求仕様（`requirement_list.md`）との追跡性を確保する。
- **直交表による網羅性検討**:
  - 公開 API の各パラメータ、エラー種別、内部状態の組み合わせについて、直交表（Pairwise / All-Pairs）を用いて網羅性を検討・記録する。

## 3. Mermaid 記法規約

- **特殊記号のクォート**:
  - ノードラベル内に括弧 `()` や角括弧 `[]`、特殊記号が含まれる場合は、構文エラーを防ぐため必ず二重引用符で囲む（例: `id["Label (Info)"]`）。
- **ステートマシン (`stateDiagram-v2`)**:
  - 複合状態の入出力遷移、自己ループ、終了状態（`[*]`）を明確に定義する。
- **シーケンス図 (`sequenceDiagram`)**:
  - `autonumber` を付与し、参加者（`actor`, `participant`）の責務分離と活性化区間を正しく対応付ける。
- **フローチャート (`flowchart TD`)**:
  - 開始・終了端子（`(["..."])`）、処理ステップ（`["..."]`）、条件判定（`{"...?"}`）の形状を使い分ける。

## 4. ドキュメント検証チェックリスト

ドキュメント作成・編集完了前に、以下の項目を確認すること：
1. [ ] コンポーネントの責務と境界が明確に定義されているか
2. [ ] 見出しや表の項目名に C++ や Python の内部型名・実装用語が混入せず、自然言語（日本語）で書かれているか
3. [ ] 静的内部ブロック図と動的図（シーケンス図／アクティビティ図／状態遷移図）がセットで定義されているか
4. [ ] 複雑な動的アルゴリズムに対し、責務重視＝シーケンス図、手順重視＝アクティビティ図が適切に配置されているか
5. [ ] 上位要求とのトレーサビリティ `{Keyword}` が維持されているか
6. [ ] ドキュメント整合性パイプライン（`spec-consistency.lock` / DocGraph）と整合しているか
