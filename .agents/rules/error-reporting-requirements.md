# 問題の報告

## 1. 原則

- 検査器の出力（AST、正規表現、ゲートの結果）だけを、問題の報告にしない。
- 報告の前に、要求と仕様を確認する。確認の結果を、報告に書く。
- 仕様が誤っている疑いがある場合は、判断を利用者に仰ぐ。実装や仕様を、勝手に直さない。

## 2. 確認の順序

1. **要求**: `docs/requires/requirement_list.md` の該当する要求を読む。要求が確認できない場合は、その旨を報告する。
2. **仕様**: 対象のコンポーネント設計書（`docs/components/**`）の該当する節を読む。仕様が要求と食い違うなら、その旨を書く。
3. **実装**: 違反の箇所を、実際のコードで確認する。検査器の出力だけで判断しない。
4. **判定**: 次のどれかに分類する。
   - 実装の誤り: 要求と仕様に一致させるため、実装を直す。
   - 仕様の誤り（または要求との食い違い）: 実装を直さず、利用者に判断を仰ぐ。
   - 要求が未確認: 推測で埋めず、未確認として報告する。
   - 検査器の誤り（誤検出）: 検査器の対象と規則を直す。

## 3. 報告の書式

報告は、次の項目を、この順序で書く。項目が確認できないものは「未確認」と書く。

| 項目 | 内容 |
| :--- | :--- |
| 結論 | 実装の誤り、仕様の誤り、要求未確認、検査器の誤り、のいずれか |
| 違反箇所 | ファイル、行、関数名。実際のコードを確認した結果 |
| 要求 | 要求の ID と、要求の文 |
| 仕様 | 仕様の文書、節、該当する文。要求との一致または食い違い |
| 禁止の理由 | 規約（`.agents/rules/`）の条項、または要求の文 |
| 対象の実装言語 | C/C++、Python、アセンブリ、など |
| 性能・計算量の要求 | 要求の文書に書かれている値。書かれていなければ「要求に記載なし」 |
| メモリの要求 | 要求の文書に書かれている RAM、ROM の値。書かれていなければ「要求に記載なし」 |
| 要求への影響 | 違反が、どの要求を満たさないか。影響がなければその理由 |
| 修正方向 | 実装の修正、または利用者への判断依頼（仕様の誤りの場合） |

## 4. 仕様の誤りが疑われるとき

- 実装を仕様に合わせて直す前に、仕様と要求の食い違いを報告する。
- 次の 3 点を書き、判断を仰ぐ。
  1. 仕様の該当箇所と、その内容
  2. 要求の該当箇所と、その内容
  3. 実装がどちらに従っているか。どちらが正しいと考えるか（根拠つき）
- 利用者の判断が出るまで、仕様も実装も変更しない。

## 5. 禁止事項

- 要求を確認せずに、「違反」と断定しない。
- 要求の正本に書かれていない性能やメモリの値を、推測して書かない。
- 仕様が誤っている可能性を、報告で伏せない。
- 検査器の出力を、そのまま報告にしない。
