# 検証の「サボり」アンチパターン・カタログ (Verification Slacking Antipattern Catalog)

このドキュメントは、形式検証・コンセプトコード・物理仕様・シミュレータの各層で実際に発見された「検証の体裁はあるが中身がない」事象からパターンを抽出し、体系化したものである。新しい検証コード・検証ゲートを書く、またはレビューする際は本カタログのマトリクスを確認し、該当しないか厳格に検査すること。
scope: GLOBAL

## 1. パターン一覧

各パターンは「これを書いた本人（Gemini/Claude等含む）は正しく検証しているつもりでも、実際には何も保証していない」という性質を持つ。

### A. 恒真アサーション (Tautological Assertion)
入力に関わらず必ず成立してしまう条件で「検証した」体裁を作る。
- 実例: `assert len(st.hex_bytes.split()) >= 0`（`len()`は負にならないため絶対に失敗しない）
- 検出法: ミューテーションテスト——検証対象を意図的に破壊し、アサーションが本当に落ちるか確認する。

### B. 自己参照比較 (Self-Referential Comparison)
独立した根拠（実行結果、別の一次情報源）ではなく、**別の場所に手で複製した値**と比較して「一致確認」と称する。
- 実例: `jit_assembler_constexpr_concept.py`のパリティテストが、実際のステンシルカタログではなく関数内に直接手打ちした16進文字列と比較していた。同じ値がカタログ側にも独立に手打ちされており、片方を編集しても検出できない。
- 検出法: 比較対象の一方が「本物の実行結果／唯一の正本」に由来しているか確認する。両方とも人力転記なら無価値。

### C. 未結線コード (Unwired Code)
テストコード自体は書かれ、実行すれば意味のある検証をするが、**どのゲート・CI・テストスイートからも呼ばれない**。
- 実例: `docs/**/concepts/*_concept.py` がテスト収集規約に合致せず、テストランナーを実行しても0件収集。パイプラインもこれらを実行しておらず、コンセプトコードが一度も自動実行されていなかった。
- 検出法: 「このテストは実際にどのコマンドから、どの頻度で実行されるか」を確認し、テストランナーやパイプラインに明示的に登録・結線する。

### D. 代理層検証 (Proxy-Layer Verification)
本物の成果物（バイト列・実行結果・実測値）ではなく、**人間可読な代理表現**（disasm文字列、ログテキスト）だけを検証する。
- 実例: シフト/ローテート系ステンシルのテストが `code[0] == "ASRS r4, r5, r4"` という文字列一致だけを見ていた。この3オペランド表記自体が実際のThumb-1 2オペランド命令では表現不可能な架空の記法で、実バイトを一度も実行していなかったためオペランド順序が逆転したバグに誰も気づけなかった。
- 検出法: 実CPUエミュレータ（Unicorn等）で実バイト列を実行し、レジスタ／メモリの最終状態を独立に計算した期待値と比較する。

### E. 正本なき数値 (Unbacked Concrete Number)
具体的な数値（バイトオフセット、アドレス等）が使われているのに、**その数値の根拠となる単一の正本が存在しない**。
- 実例: JITステンシルカタログが `[r2, #0x00]`（グローバル）・`[r2, #0x04]`（メモリサイズ）を決め打ちしていたが、`vsoc_runtime`のフィールドレイアウトを定義したドキュメントがどこにも存在しなかった。
- 検出法: コード中の `[Rn, #imm]` 形式の即値オフセットすべてについて、対応する構造体定義（オフセット表）へのリンクを要求する。

### F. 過大な地の文主張 (Overclaiming Prose)
実際には行われていない検証プロセスやビルドを、地の文で断定的に記述する。
- 実例: `jit_stencil_catalog.md`が「ビルド時にClang 17で生成されたバイナリ列」と記載しているが、実際にそのようなビルドパイプラインは存在しない。
- 検出法: 「検証済み」「100%一致」「ビルドで生成」等のキーワードに対し、裏付けとなる実行可能な成果物（レポート、モデル、ビルドログ）へのリンクを要求する。

### G. 層をまたいだ不整合の不可視化 (Cross-Layer Contradiction)
個々の文書・個々のコンポーネント単体では矛盾していないが、**要求仕様と具象実装を横断して初めて見える矛盾**。単一レイヤーのレビューでは発見できない。
- 実例1: `{MemoryBoundaryCheck}`要求は「境界チェックが生成コードに埋め込まれる」と主張し、`jit_compiler.md`もそう説明しているが、実際のJITステンシル（`ldr.w r4, [r3, r4]`）にはマスク／比較命令が一切ない。
- 実例2（さらに悪化した再発）: 実例1を修正する際、Markdown仕様だけを書き換え、実行・検証済みのコンセプトコードは一切変更しなかった。静的監査はMarkdownしか読まないため、この不一致を検出できずPASSと誤判定された。
- 検出法: 仕様変更時は必ず対応するコード（コンセプトコード、テストコード等）を同一コミットで同期して更新する。

### H. 分母のズレ (Wrong-Denominator Coverage)
カバレッジ率・discharged数の**分母（何を100%とみなすか）が実体とズレている**ため、高い数値が出ても実際の網羅性を意味しない。
- 実例: `min_length`フィルタにより一部セクションが恒常的に評価対象外になるにもかかわらず、厳格モードは「全セクション評価済み」を要求し続ける。
- 検出法: 分母となる対象母集団が正しく定義されているかを監査し、フィルタによる除外条件と合格条件の整合性を確認する。

### I. 具象なきワイルドカード型注釈 (Wildcard Type Masking / Any-Escaping)
静的型チェッカー（mypy / pyright / ruff）の警告を回避するために `typing.Any` や緩いキャストを濫用し、**「型チェックをパスしている」という偽りの安心感を作り出しながら、実際にはランタイムエラーのリスクを完全に隠蔽する**。
- 実例: シミュレータおよびコンセプトコード内で `data: Any`, `cb: Callable[..., Any]` を多用し、不正なオブジェクトや未定義属性へのアクセスが静的解析をすり抜けて本番シナリオ実行時に初めて例外クラッシュを引き起こした。
- 検出法: コードベース全体で `typing.Any` の使用を 0 件に制限（完全禁止）し、具体的なクラス名、具象型、または代数的データ型（`Never` を含む `Result`）の明示を義務付ける。

### J. 抽象仕様への特定言語実装用語の混入 (Language-Specific Leakage in Specs)
言語非依存であるべき設計仕様書（`docs/components/**`）に、**特定の実装言語・シミュレータに依存した型名や内部データ構造用語を無批判に持ち込み、アーキテクチャのポータビリティや概念の明確性を損なう**。
- 実例: 設計仕様書に C++ に存在しない Python 固有の型名（`bytearray`）や、実装詳細用語（`(AoS)`）が混入し、C++ 本実装時に参照すべきデータ表現が曖昧になっていた。
- 検出法: 設計仕様書の見出し・項目名・記述はすべて自然言語（日本語）で概念・意図・不変条件を記述し、C++ や Python 固有の内部実装用語を混入させない。

## 3. 今後の運用規律

- **ミューテーションテストの維持**: 形式検証モデルにおける `guards=False` 変異検査により、反証性（仕様違反を確実に検出できること）を永続的に担保する。
- **同一コミット原則の遵守**: ドキュメントと実装（コード・テスト）が乖離する層間矛盾（G）を防止するため、仕様修正とコード修正を必ず同一コミットで揃える。
- **型安全性と自然言語仕様の死守**: コードにおける `Any` 排除（I）と、仕様書における自然言語徹底（J）をレビューおよび静的検証の必須基準とする。
