# 最上位アーキテクチャ監査ルーブリック (Architecture Review Rubric)

本ルーブリックは、最上位アーキテクチャ設計書（`docs/architecture/architecture_overview.md`）が、下位の各コンポーネント詳細仕様書（Tier 1〜3）、形式検証モデル、WIT定義、コンセプトコード、および実装コードと完全一致しているかを評価するための**観点基準**を定めます。

> [!IMPORTANT]
> **仕様値非保持の原則**:
> 本ルーブリック内に具体的なバイト数、オフセット、レジスタ番号、アルゴリズムの詳細等の「仕様そのもの」を記載してはならない。仕様の具体値を書くとルーブリック自身が仕様分裂の温床となる。本ルーブリックは**突合・検証すべき観点と判定基準のみ**を定義する。

---

## 1. 重要度分類 (Severity Levels)

- **CRITICAL (致命的 / 仕様分裂)**:
  - 最上位概要と下位仕様書／WIT／コード間で、バイトサイズ、オフセット、レジスタ番号、またはメモリレイアウトが真っ向から食い違っている。
  - 形式検証モデルで証明された不変条件や安全機構のセマンティクスと矛盾する制御フローが記載されている。
- **MAJOR (主要改善 / 更新漏れ)**:
  - 最上位概要内の図（Mermaid）と本文記述・下位仕様の間に矛盾が存在する（本文改定に伴う図の更新漏れ）。
  - 下位仕様書やADRで確定した設計変更（保護方式の改定、ムーブセマンティクス統一等）が最上位概要に反映されず放置されている。
  - 廃止された旧設計やドラフト時の概念・クラス名が残存している。
  - 定義元正本アンカーの配置場所が `keyword_dictionary.md` の指定と乖離している。
- **MINOR (軽微 / 推奨改善)**:
  - 表記の微細な揺れ、コメント・図のキャプションの補足不足。
  - 文脈上自明なキーワードリンクの追加推奨。

---

## 2. 5大監査観点 (Evaluation Dimensions)

### 観点 1: 最上位と下位仕様の垂直整合性 (Vertical Specification Consistency)
- **記述の完全一致**:
  最上位アーキテクチャ概要の記述（システム構造、コンテキスト定義、レジスタ役割、メモリ領域分割等）が、下位コンポーネントの個別詳細仕様書（Tier 1 Core, Tier 1 Interface, Tier 2 Runtime, Tier 3 JIT, Tier 3 Platform）の記述と完全一致しているか。
- **仕様改定の追随漏れ検知**:
  下位仕様書の改定（または最上位概要の改定）に伴い、一方のみが更新されて他方が取り残されている「仕様分裂（Specification Drift）」がないか。

### 観点 2: 物理リソース・レイアウト定義の単一正本性 (Single Source of Truth for Layouts)
- **メモリレイアウト・レジスタ規約の単一性**:
  構造体のバイトサイズ、フィールド並び順、アライメント、物理レジスタの役割分担が、最上位概要、個別仕様書、WIT定義、およびコンセプト/実装コードの間で一切の矛盾なく1対1で対応しているか。
- **定義元アンカーの適正配置**:
  `keyword_dictionary.md` で定義元正本（Source of Truth）と定められているアンカー（`{...}`）が、真の定義箇所に正確に配置され、他のドキュメントからはリンクとして参照されているか（アンカーの二重定義や定義元違いの排除）。

### 観点 3: 制御フロー・動的モデル・不変条件の一致性 (Dynamic Invariant Parity)
- **動的挙動の整合性**:
  最上位概要に記載された動的プロトコル（キャッシュ昇格・代謝規則、ディスパッチ手順、IPCランデブー手順、ハードウェア境界保護機構等）が、下位仕様書のアクティビティ図／シーケンス図および形式検証モデル（CTL/LTL特性式）と矛盾なく整合しているか。
- **図と本文・下位仕様の完全一致性 (Diagram-Content Parity)**:
  最上位概要に掲載されている Mermaid 図（アーキテクチャ階層図、シーケンス図、フローチャート、メモリレイアウトブロック図等）が、最上位概要の本文解説、手順説明、表定義、および下位仕様書の内容と矛盾なく完全一致しているか（本文改定時の図の追随漏れ・陳腐化の完全排除）。
- **安全保護セマンティクスの統一**:
  メモリ安全性、排他制御、所有権移譲などの抽象設計概念（例: マッピングの有無によるハードウェア遮断、言語レベルのムーブセマンティクスによる二重所有排除等）が、システム全体で統一された論理モデルとして記述されているか。

### 観点 4: メタキーワード・トレーサビリティの完全性 (Traceability & Anchor Completeness)
- **キーワード台帳との完全同期**:
  アーキテクチャ概要内のすべてのメタキーワード（`{...}`）が `keyword_dictionary.md` に登録されており、要求仕様書（`requirement_list.md`）の要求ID・ADR（設計決定）・GOTCHA（設計の勘所）と正しく紐付けられているか。
- **リンク切れ・未結線の不在**:
  アーキテクチャ概要から参照されている下位コンポーネントや WIT、形式モデルへのリンク・言及に欠落やリンク切れが存在しないか。

### 観点 5: 旧ドラフト設計・廃止要素の完全排除 (No Stale Drafts or Deprecated Fallbacks)
- **検討段階のドラフト残存検知**:
  過去の設計検討フェーズで策定されたが、その後のADRで廃止・改定された旧クラス名、旧API、旧引数規約、旧データ構造、および不要な後方互換用フォールバックの記述が残存していないか。

## 3. 判定基準 (Grading Criteria)

| 判定 | 基準 |
| :--- | :--- |
| **PASS** | 全監査観点において仕様分裂、数値乖離、旧ドラフトの残存がなく、最上位と下位仕様が完全整合している。 |
| **WARN** | 基本設計に影響しない軽微な表現揺れ、補足説明の軽微な不足、または優先度の低い改善点のみが存在する。 |
| **FAIL** | 以下のいずれかに該当する重大な欠陥（CRITICAL / MAJOR）が 1 件以上存在する。 |
