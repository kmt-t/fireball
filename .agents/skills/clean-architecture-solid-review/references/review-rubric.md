# Clean Architecture / SOLID クラス設計レビュー基準

## 1. 正本とレイヤーの確定

一般的な Clean Architecture の図を先に当てはめず、対象リポジトリの要求・アーキテクチャ・コンポーネント仕様を正本として読む。

Fireball では {CleanArchitecture} の要求、docs/architecture/architecture_overview.md の依存性ルール、docs/architecture/document_structure.md の Tier 定義・上り依存禁止・契約/実装分割基準を確認する。Tier は文書の抽象度と責務分解を表し、Tier 番号だけで同心円レイヤーを決めない。Architecture Overview では Kernel Layer (COOS, IPCR) を Inner、App/Svc/vSoC/HAL/Log/HW を Outer としているため、その定義と各コンポーネント仕様を照合する。

対象クラスの所属をポリシー／契約、アプリケーションのユースケース・統合、アダプタ／ランタイム詳細、プラットフォーム詳細など、プロジェクトが採用する語彙で記録する。契約と実装を別仕様に分けている場合は、契約を所有する側と実装を提供する側を別々に追跡する。曖昧ならレイヤー割当てを断定せず、根拠と未確認事項を示す。

## 2. 責務、計算量、簡潔さ

各クラス／構造体について、誰の要求や方針を実現するか、独立して変わる複数の理由・アクター・状態機械を抱えていないか、保持状態と操作が同じ不変条件・ライフサイクルを扱っているかを確認する。API が利用側の契約だけを表しているか、他コンポーネントの内部処理やテスト専用フックを抱えていないかも追う。

責務設計と合わせて、支配的な計算量と資源コストを調べる。

- ホットパスの時間計算量、繰返し走査、ネストした探索、再計算、不要なソートやコピーを確認する。平均値だけでなく、入力上限と worst-case の計算量・レイテンシを記録する。
- 空間計算量、最大容量、固定配列・キャッシュ・インデックスの追加領域、一時データ、アロケーション、スタック使用を見積もる。
- クラス分割や抽象層追加が呼び出し段数、間接参照、重複状態、ヘッダ依存、コード生成量を増やすかを比べる。必要な計算量改善を、ハード制約や仕様を破る「小ささ」と交換しない。
- コンパクトさは短い行・圧縮記法・凝集度のない巨大関数を意味しない。重複を減らし、余分なクラス、インターフェース、変換層、状態・データコピーを避けつつ、名前と境界で意図を追える構造を評価する。
- 小さくまとまった状態と不変条件はむやみに分割しない。別々のアクター、寿命、計算量要件、変更理由を持つ責務を、一つに詰め込むことも正当化しない。
- 一般化、キャッシュ、インデックス、Factory を提案するなら、測定値または明確な計算量根拠、容量、更新コスト、使用頻度、設計上の必要性を示す。将来の拡張可能性だけで複雑さを足さない。

## 3. 依存方向と DIP

ソース依存と実行時呼び出しを分けて静的依存グラフを作る。include/import、基底型、テンプレート引数、関数ポインタ、callback、データ型の受け渡し、所有権、生成箇所を追う。

- 内側の方針・契約が外側の具象クラス、OS/ハードウェア API、特定実装へ依存していないか。
- 外側の実装が内側の契約を実装し、呼び出し側が契約経由で使っているか。
- インターフェースが実際に依存を反転しているか。名前だけの抽象型を追加して具象依存や循環を残していないか。
- 依存注入が明示的か。隠れたグローバル、サービスロケータ、テスト時だけ異なる分岐を通じて結合していないか。
- 低位の層が高位の利用シナリオを import する、または高位の層が低位実装の内部詳細を直接握る関係がないか。

DIP はすべてを抽象型にする規則ではない。境界の安定性、独立して変わる実装、テスト／移植要件、追加される ROM/RAM・呼び出しコストを踏まえ、具象型への依存がポリシーを不安定にする箇所に適用する。組み込み C++ では静的 Harness、関数ポインタテーブル、テンプレート等が抽象境界を実現する場合がある。仮想関数を使わないという理由だけで DIP 違反にしない。

## 4. Factory と Composition Root

生成責務を、オブジェクトの不変条件を成立させる処理と、具象依存を選択してオブジェクトグラフを組み立てる処理に分ける。

### Composition / dependency wiring factory

依存実装の選択、プラットフォーム／構成に応じた具象型の束ね、レイヤーを跨ぐ配線を行う Factory は、原則として対象ポリシーレイヤーの外側、Composition Root、起動コード、Harness、または Adapter 側に置く。外側は内側の契約と具象詳細を知ってよいが、内側のポリシーが外側の Factory や具象 Adapter を呼び、自身を組み立てる形にしない。

Factory が具象依存をどこから知るか、どの層の型を返すか、ポリシーを漏らさず契約で受け渡しているか、実行時判断やドメイン規則まで抱えていないか、Composition Root が散在して所有権や生成順を曖昧にしていないかを確認する。

### Domain/entity factory

内側の Factory が常に誤りとはしない。複雑な生成規則や不変条件がドメイン／ポリシーそのものに属し、入力・返却型が内側の型で閉じ、外側のプラットフォーム実装や DI コンテナを知らない場合は内側に置く理由がある。単純な constructor 呼び出しを包むだけなら、その付加価値と間接層・コード量を確認する。

## 5. SOLID の適用方法

### S — Single Responsibility

変更理由、アクター、状態機械が独立しているかを見る。複数メソッドや collaborator があるだけでは違反としない。仕様上の不変条件や独立した変更理由を根拠にする。

### O — Open/Closed

既知の変化点へ新実装を加える際、安定した無関係のポリシーを改変せず拡張できるかを見る。opcode、エラーコード、デバイス種別など固定集合への switch は仕様・性能・コードサイズ上妥当な場合がある。将来の仮想拡張性だけのために抽象階層を加えない。

### L — Liskov Substitution

実装を差し替えても、事前条件、事後条件、不変条件、エラー契約、寿命・所有権が保たれるかを見る。継承に限らず Harness callback や静的ポリシー型にも契約検査を適用する。代替実装がない場合に置換可能性の問題を推測しない。

### I — Interface Segregation

呼び出し側が不要な操作・依存・型を知る必要がないかを見る。利用側ごとに責務の異なる操作群があれば契約分割を検討する。1 メソッドずつの細分化や、利用側が一つだけという理由の分割は求めない。

### D — Dependency Inversion

高位方針が低位詳細に依存していないか、抽象がポリシーの契約を表すか、具象実装がその契約に従うかを確認する。抽象追加が実際にソース依存を変えるか追う。

## 6. Fireball の実装制約

対象言語に応じて .agents/rules/coding-standards-cpp.md、.agents/rules/coding-standards-python.md を読み、抽象化案を制約に照らす。

- C++ では通常の new/delete や malloc 系 API、標準動的 STL コンテナ、例外、RTTI が禁止される。必要な差し替えは固定容量・静的 DI を優先し、ABI、所有権、実行時コストを記録する。
- pysim では Any、製品コードの built-in dict/set/list、テスト専用フック等の既存規約を守る。クラス設計に無関係な抽象を足さない。
- テスト用 Fake/Stub はテスト側に置き、製品コードへテスト専用分岐や生成 API を追加しない。
- 文書・仕様とコードが矛盾する場合は、正本と明示された契約を先に特定する。将来計画で現行違反を免除しない。

## 7. 指摘の重大度とレポート

- **CRITICAL**: 確定した境界に反して内側ポリシーが低位具象へ依存し、セキュリティ境界、責務分離、変更隔離を実際に破壊している。循環依存や契約逆流が仕様・ビルド・重要なテストを壊す場合。
- **MAJOR**: 複数の独立した変更理由や状態機械の混在、配線 Factory がポリシーレイヤーへ具象依存を漏らす、重要な利用側に不要な操作が強制される、または測定／計算量根拠のない複雑さが性能・メモリ上の有意な負担となるなど、具体的な修正を要する設計欠陥。
- **MINOR**: 境界・生成経路の説明不足、不要だが影響の小さい抽象層、複雑度やコード量の改善余地。好みだけの指摘は含めない。

各 finding はファイル・行、該当クラス／依存経路、違反する原則、実害、最小の修正案、関連テストまたは確認方法を含める。測定や仕様で確定できない推論は「要確認」と付ける。良好な設計も短く記録し、問題数を増やすために違反を作らない。

レポートは対象範囲、レイヤー割当て、依存関係の要約、Factory 配置、SOLID 所見、計算量と簡潔さ、重大度順の指摘、未確認事項を含める。CRITICAL があれば FAIL、CRITICAL なしで MAJOR があれば WARN、CRITICAL/MAJOR がなければ PASS とする。
