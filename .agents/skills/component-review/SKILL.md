# Component Review

## 目的

本スキルは、仕様の必要性と既存機構への適合を確認し、次の証拠を一続きの設計チェーンとして評価する。

1. 仕様書（Markdown）
2. 形式検証モデル（`pyModelChecking`）
3. コンセプトコード（Python）
4. テスト仕様とテストコード

## 対象

対象はユーザーが指定したコンポーネントと、そのチェーンに直接関係する WIT・親 `FORMAT.md`・要求・ルールである。個別モジュールの全体監査は、指定がない限り含めない。

## 手順

1. **チェーンを収集する**: コンポーネント名または仕様書パスから関連ファイルを特定する。

   ```bash
   uv run python .agents/skills/component-review/scripts/collect_chain.py <component_name> --json
   ```

   出力された specification、formal、concept、test_spec、WIT、`contract_only`、欠落証跡を実ファイルと照合する。

2. **正本と形式を確認する**: 仕様書には [`docs/components/FORMAT.md`](../../../docs/components/FORMAT.md)、テスト仕様書には [`docs/qa/FORMAT.md`](../../../docs/qa/FORMAT.md) を適用する。設計意図とFORMATが食い違う場合は、どちらが古いかを根拠から判定する。

3. **仕様の必要性を判定する**: [仕様の必要性と既存機構の確認](../specification-review.md) を適用する。対象契約を要求・不変条件と既存経路へ対応付ける。実装・結線・検証の不足と、契約の追加が必要な問題を分ける。

4. **各層を確認する**: [垂直検証ルーブリック](references/evaluation_rubric.md) と [検証アンチパターン](../../rules/verification-antipatterns.md) の全適用項目を、仕様、形式モデル、コンセプト、テストの順に確認する。独立した層は利用可能な場合に並行監査し、結果を同一ルーブリックで統合する。

5. **層間を照合する**: 状態、制約、API、キーワード、証拠リンク、テスト条件が各層で一致するか確認する。矛盾がある場合は上位の正本から下位への追随を判定する。

## チェックリスト

- 仕様、図、例示コードと形式モデルの状態・性質が対応する。
- `guards=False` 変異で保護条件の破壊が検出される。
- コンセプトコードが形式モデルと仕様に忠実で、`typing.Any` がない。
- テストが境界・状態遷移・GOTCHA を実際の状態や副作用で検証する。
- evidence、`BACKS`、WIT、テスト仕様、親FORMAT、層間参照が結線している。
- 契約のみのコンポーネントでは `contract-only: true` を確認し、実装層は実装側コンポーネントで監査する。形式検証・テスト・WIT の証拠は引き続き確認する。
- `docs/**/concepts/` では標準 `dict` / `set` / `list` を許容する。pysim 専用のコンテナ禁止規約やスキャナを適用しない。

## 結果

[共通レビュー手順](../review-protocol.md) の所見形式と判定を使う。仕様の必要性の判定も報告する。修正案には共通の必要性確認を再適用する。全適用項目の判定と根拠、欠落証拠、層間矛盾、未確認の範囲と必要な追加調査を報告した時点でレビュー完了とする。
