# 垂直検証チェーン評価ルーブリック (Vertical Chain Evaluation Rubric)

本ドキュメントは、コンポーネントの「仕様書（Markdown） → 形式検証（pyModelChecking） → コンセプトコード（Python） → 単体テスト（Test Spec / Tests）」の4層設計における正しさと階層間一貫性を評価・採点するための標準ルーブリックである。

---

## 1. 階層別評価基準

### 1.1 仕様書層 (Layer 1: Specification)
- **自然言語（日本語）仕様の徹底 (`rules/documentation-standards.md`, Antipattern J)**
  - 見出し、表の項目名、地の文が自然言語で書かれているか（C++の内部型名、Pythonの `bytearray` 等が混入していないか）。
  - コード名、API シンボル名、メタキーワード、URI のみ英語が使用されているか。
- **静的・動的設計のペアリング (Bonsai Design Step 0)**
  - 静的構造図（`graph TD`）と動的振る舞い図（`sequenceDiagram` / `flowchart TD` / `stateDiagram-v2`）が正しく配置されているか。
  - 責務重視＝シーケンス図、手順重視＝アクティビティ図（`flowchart TD`）の使い分けが守られているか。
- **図と本文・仕様記述の完全一致性 (Diagram-Text Consistency)**
  - 仕様書内の Mermaid 図（`graph TD`, `sequenceDiagram`, `flowchart TD`, `stateDiagram-v2`）が、本文の自然言語解説、手順記述、および表定義と矛盾なく完全一致しているか。
  - 図内のノード名、状態名、遷移条件、メッセージ送受信順序、引数・戻り値が、本文記述やアルゴリズムと 1 対 1 に対応しているか。
  - 本文を改定した際に図の更新が漏れ、過去の旧設計が図に残存していないか（図の陳腐化・乖離の完全排除）。
- **ドキュメント中の例示コード・擬似コードと本文の完全整合性 (Code Example-Text Consistency)**
  - 仕様書内に記載されている例示コード・擬似コード・API使用例のシグネチャ、引数、戻り値、制御フロー、定数名が、本文の自然言語解説、手順説明、表定義と矛盾なく完全一致しているか。
  - 本文やAPI定義を改定した際に例示コードの更新が漏れ、過去の旧仕様・廃止された引数や型が例示コードに残存していないか（例示コードの陳腐化・乖離の完全排除）。
  - ドキュメント内の例示コードが、リファレンス実装（コンセプトコード・WIT定義）の最新インターフェースと整合しているか。
- **不変条件・境界条件の明示**
  - 単一所有権、境界チェック、エラー処理、リカバリー戦略が明確に定義されているか。
- **メタキーワードとトレーサビリティ**
  - `{Keyword}`、`<!-- traceability: ... -->`、`<!-- evidence: ... -->` が正しく宣言されているか。

### 1.2 形式検証層 (Layer 2: Formal Verification - pyModelChecking)
- **Kripke 構造の妥当性**
  - 状態集合 $S$、初期状態 $S_0$、遷移関係 $R$、原子命題ラベル $L$ が仕様書の動的設計（状態遷移図）と 1 対 1 に対応しているか。
  - 状態爆発を招かないよう適切に抽象化されているか。
- **CTL/LTL 特性式の厳密性**
  - 安全性（Safety: `AG(Not(deadlock))`, `AG(Not(double_owned))` 等）が過不足なく定式化されているか。
  - 活性（Liveness: `AG(AF(main_loop))` 等）が無限ループ・餓死を防ぐ形で定式化されているか。
- **反証可能性と変異検査 (Antipattern A: 恒真アサーション排除)**
  - `build_model(guards=False)` などの変異モデルが実装され、意図的にガードを外した際に特性式が反証（`model_check` が False を返すこと）されるか。
  - 恒真アサーション（常に True になる無意味な式）になっていないか。

### 1.3 コンセプトコード層 (Layer 3: Concept Code)
- **モデル・仕様への忠実度 (Fidelity)**
  - 形式検証モデルで証明された状態遷移・ハンドオフ制御・排他条件がコードの制御フローに漏れなく実装されているか。
  - 抽象仕様で宣言された定数（`FB_CONF_*`）やインターフェースと一致しているか。
- **型安全性の死守 (Antipattern I: Any-Escaping 完全禁止)**
  - `typing.Any` が 0 件であるか。
  - 具象クラス、Union、ジェネリクス、または代数的データ型で厳格に型付けされているか。
- **検証サボりアンチパターンの排除**
  - **自己参照比較 (Antipattern B)**: 手打ちの重複データ同士の一致確認をしていないか。
  - **未結線コード (Antipattern C)**: 実行可能なエントリポイント（`__main__` やテスト関数）が用意されているか。
  - **代理層検証 (Antipattern D)**: 実バイナリや実状態ではなくダミーの文字列一致だけで済ませていないか。
  - **正本なき数値 (Antipattern E)**: 根拠のないマジックナンバー・オフセットが存在しないか。

### 1.4 単体テスト・テスト仕様層 (Layer 4: Test Spec & Tests)
- **直交表・マトリクス網羅性 (Combinatorial Coverage)**
  - 直交表（Pairwise / All-Pairs）で正常系・異常系・境界条件が網羅されているか。
  - 状態遷移の全エッジ（到達不能ケースのアサーション検出含む）がテストケースにマッピングされているか。
- **GOTCHA（実装の勘所）の検証**
  - 仕様書やテスト仕様書に記載された GOTCHA（落とし穴・不変条件）を実証するテストが存在するか。
- **アサーションの真実性**
  - 期待値が独立した計算・真の仕様に基づいているか。
  - テストが形骸化していないか（偽陰性・偽陽性の不在）。

## 2. 層間一貫性・垂直トレーサビリティ評価基準 (Cross-Layer Parity)

| 検査項目 | 検証内容 | 判定基準 |
| :--- | :--- | :--- |
| **CL-01: 状態名・用語・図・例示コードの一貫性** | 仕様書の図（Mermaid）、例示コード・擬似コード、形式モデルの状態名、コードの Enum、テストケース名が完全に整合しているか | 命名ブレ・図や例示コードとモデルのズレがないこと |
| **CL-02: 定数・制約の一貫性** | バッファサイズ、連続ハンドオフ上限等の定数が4層で同一値・同一意味であるか | 不整合は上位 Tier を正本として解決 |
| **CL-03: エビデンスヘッダー整合性** | 仕様書ヘッダーの `<!-- evidence: ... -->` に記載されたパスが実在し、各コード側からも逆リンク（`BACKS = [...]` 等）されているか | リンク切れ・未結線がないこと |
| **CL-04: 層間矛盾 (Cross-Layer Contradiction, Antipattern G)** | 仕様書の主張とコンセプトコード・テストコードの実際の振る舞いに食い違いがないか | 一方を修正して他方を放置していないこと |
| **CL-05: クリーンアーキテクチャ依存規則** | 上位 Tier（要求・方針）が下位 Tier（実装詳細・言語仕様）に依存していないか。特に契約/実装分割パターン（`document_structure.md` §2.1-4）を適用したコンポーネント対（例: `system_memory.md`（Tier1契約）↔ `runtime_memory.md`（Tier2実装）、`hal_dispatch.md`（Tier2抽象化層）↔ `platform_driver.md`（Tier3ドライバ実装））で、契約側が実装側の具象データ構造・物理レイアウトを記述していないか | 常に上位が正本（下位の誤記・追随漏れとして解決） |
| **CL-06: Tier間波及チェック (Tier Propagation Check)** | コンポーネントの Tier 再配置・契約/実装分割・ファイル改名が行われた際、エビデンスヘッダーの逆参照（`BACKS = [...]`）、`keyword_dictionary.md` の対象コンポーネント列、他コンポーネントからの相互参照（正本リンク・URI・ファイルパス言及）のすべてが新配置に追随しているか | 旧 Tier・旧ファイル名を指したままの参照（ダングリング参照）が1件も残存しないこと |
| **CL-07: キーワード定義/参照配置 (Keyword Definition/Reference Placement)** | `document_structure.md` §4.4 の上位/下位キーワード表記規約（定義元＝見出し明示、参照側＝本文インライン）が、契約/実装分割コンポーネント対で適用されているか | 定義元コンポーネントの見出しに対象キーワードが明示され、参照側が本文インラインで引用する形になっていること（未移行のキーワードは MINOR に留める） |

## 3. レビュー結果の重要度（Severity）分類

- **CRITICAL (重大な欠陥 / ブロッキング)**:
  - 形式検証で証明された安全性・活性がコンセプトコードで破壊されている。
  - 変異検査（`guards=False`）が機能しておらず、恒真アサーションになっている。
  - 仕様書とコードで境界条件や状態遷移が真っ向から矛盾している（層間矛盾）。
  - `typing.Any` の使用。
- **MAJOR (主要な改善項目)**:
  - 仕様書内の図（Mermaid）と本文記述・手順が矛盾している、または本文改定に伴う図の追随漏れ（図の陳腐化）が存在する。
  - 仕様書内の例示コード・擬似コードと本文記述・表定義・最新APIのシグネチャが矛盾している、または本文改定に伴う例示コードの追随漏れ（例示コードの陳腐化）が存在する。
  - 直交表に記載された境界テストケースが未実装。
  - 仕様書見出しや表に実装言語用語（C++型名、Python型名等）が漏れ出ている。
  - エビデンスヘッダーに記載されたファイルへの逆参照（`BACKS`）が欠落。
  - GOTCHA に対応するテスト検証が不足。
  - Tier再配置・ファイル改名後に、旧パス・旧ファイル名を指したままのダングリング参照が残存している（CL-06）。
  - 契約/実装分割コンポーネント対でキーワード定義/参照配置規約（CL-07）が未適用（ただし移行未着手のキーワードは MINOR）。
- **MINOR (軽微な指摘 / 推奨事項)**:
  - Mermaid 図のラベルクォートのスタイル不統一。
  - コメントやDocstringの補足説明の不足。
  - リファクタリングによる可読性向上の余地。
