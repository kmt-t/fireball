# 仕様の必要性と既存機構の確認

仕様の追加・改定・レビューで、要求を満たす最小の契約と責務を確認する。
architecture-review と component-review は、層間の整合性を判定する前に本手順を適用する。
本手順はレビュー方法を定める。製品の新しい要求や実行機構は定義しない。

## 1. 判定前に揃える根拠

1. 最新のユーザー指示と、要求・文書階層・対象コンポーネントの正本を確認する。
   既決の判断と未決事項を分ける。仕様へ未反映の合意も、既存本文と区別して扱う。
2. 対象範囲の状態、API、配送経路、補助表、復旧処理、保証を要求や不変条件へ対応付ける。
   共通の根拠を持つ項目はまとめてよい。変更レビューでは追加・変更された契約をすべて含める。
3. 関連するキーワード、API、同義の用語を検索する。ヒットした本文・表・図と参照先を読む。
   親契約、呼出元、責務を持つコンポーネントまで辿る。検索結果の抜粋だけで決定しない。
4. 問題の経路を、発生元から結果の観測まで追う。
   各境界について実行主体、所有者、事前条件、制御の受渡し、完了条件を記録する。
   フックや登録表は構成時と実行時を分ける。所有権移譲は移譲前・保留中・移譲後を分ける。

参照した正本のパス・行と経路が、判定を再確認できる根拠になる。
仕様で決まる事実は、この調査で解決する。
ユーザーへ問うのは、調査後も残る要求や選択肢に限る。
回答済みの判断は、その適用範囲を確認して使用する。

## 2. 必要性の判定

既存の仕様項目とレビュー側の修正案に、次の判定を付ける。

| 判定 | 必要な根拠 | 対応 |
| :--- | :--- | :--- |
| 既存維持 | 要求または成立に必要な不変条件と、責務・適用条件が対応する | 正本と証拠の対応を維持する |
| 実装修正 | 既存契約が問題を解決でき、実装・結線・検証に不足がある | 既定経路を修正し、要求された結果を直接検証する |
| 記述修正 | 動作契約は既決で、図・例・用語・参照や下位記述が追随していない | 正本へ揃え、参照を整える |
| 追加候補 | 未達の要求と、既存機構では満たせない具体的な条件を示せる | 新しい契約と責務を最小範囲で提案する |
| 削減候補 | 重複、既決契約との矛盾、または不要な責務を根拠付きで示せる | 正本への参照、既存機構への統合、削除のいずれかを提案する |
| 未確認 | 正本の探索や契約の追跡が不十分で、必要性を判断できない | 未確認箇所と次に調べる証拠を示す |

必要性は「その仕様項目を取り除くと、どの要求・不変条件・有効な利用条件が破れるか」で確認する。
上位要求に同じ文言がなくても、境界検査や内部不変条件を成立させる制約には根拠がある。
内部不変条件は、上位契約を守るために必要な条件として説明する。
追加する機構自身の成立条件だけを、その機構を追加する根拠にしない。
削減候補には、必要な保証を残す場所と、参照・証拠への影響を示す。
未確認の項目を不要と断定しない。

追加候補には、次の情報を揃える。

- 未達の要求、またはユーザーが明示した新しい要求。
- 既存の経路と、それで要求を満たせない条件。
- 追加で満たす動作・不変条件、その観測境界、責務を持つコンポーネント。
- 増える状態、API、表、分岐、検証義務と、通常経路への時間・RAM・ROMの影響。
- 同時に置換・統合する契約と、残る契約の関係。

影響は定性的でもよい。容量や時間の数値には正本または計測根拠を示す。
「安全のため」「将来必要」「テストしやすい」だけでは追加の必要性を判定できない。
既存経路の結線や検証の不足は、まず実装修正として評価する。

## 3. 見落としから仕様を増やすパターン

各項目は適用範囲の正本で判定する。例を製品の一律の方針へ変換しない。

| パターン | 確認すること | 判定の方向 |
| :--- | :--- | :--- |
| 既存機構の見落とし | 既存のフック、登録、配送、待機、借用が問題を解決するか | 結線不足なら既定経路を修正する。競合する第2の機構を追加候補から外す |
| 観測する境界の混同 | 同期・非同期、実行粒度、停止位置を誰が観測するか | 境界ごとの完了・再開条件を確認する。異なる境界の契約が両立するかを調べる |
| 所有者・変更主体の欠落 | 誰が変更し、その時点で誰が所有・借用しているか | 有効な所有期間と呼出元の責任を確認する。無効なアクセスの継続を前提にしない |
| 契約違反後の根拠なき継続 | 継続に必要な不変条件を再確立できるか | 規定された停止・assert・エラー処理に従う。回復経路には事前条件を復元する根拠を求める |
| 条件のない完了保証 | 外部の応答・公平性・停止確認に必要な仮定があるか | 保留中の安全性と完了性を分ける。タイムアウトと操作停止を別々に確認する |
| 実装・テスト都合の要求化 | 便利なAPIや現在の実装を、要求の根拠にしていないか | 正本から期待結果を導く。テスト補助や検証不足を製品契約に混ぜない |
| 局所機能による通常経路の変更 | 構成時に選べる機能が、通常経路へ状態・分岐・コピーを増やすか | 既存の構成・合成・フック境界を確認し、要求された性能を維持する |
| 契約の複製・責務の二重化 | 同じ保証を別の文書・層・名前で独立に定義しているか | 正本を一つにし、適用範囲の異なる契約は差を明示する |

契約違反、外部からの不正入力、仕様が許す資源不足は、適用契約から区別する。
assert と回復可能なエラーのどちらを使うかも、その契約に従う。
復旧を提案する場合は、サービスの再初期化、未完了要求の整理、要求の再実行を分ける。
再実行には、既決の方針と副作用の重複に関する契約を確認する。

### 境界を確かめる例

- 命令位置でのデバッグ停止は、構成時のフックと停止条件から追う。
  通常実行がランタイムへ戻る粒度との関係は、実行契約から確認する。
- ゲストの同期APIは、ゲストへの復帰条件を確認する。
  内部の非同期処理・タスクのサスペンドと両立するかを確認する。
- 割り込みの起床先索引と、受信側の処理・後続配送の判定を分けて追う。
  索引の改善が配送方針を変える必要があるかを確認する。
- ビューの寿命は、変更主体と所有権移譲から追う。
  借用期間外の利用を支える追加メタデータの必要性は、その利用要求から判定する。

## 4. 報告と完了条件

対象契約、要求・不変条件の根拠、既存経路と責務、判定を対応付けて報告する。
追加・削減の所見には、最小の対応案と、その案が破り得る既存契約を添える。
レビュー側の対応案にも本手順を適用する。
新しい機構を勧める案は、追加候補の根拠を満たす必要がある。

同じ要求を満たす重複経路は、同じ原因の所見としてまとめる。
確定した違反の重大度は[共通レビュー手順](review-protocol.md)に従う。
必要性・責務・矛盾に関する重要な未確認事項が残る場合は、判定保留と明記する。
その範囲を適合またはPASSとして扱わない。

各対象に判定と根拠、または未確認の範囲と不足する証拠を示し、修正案を同じ基準で確認すればレビュー完了である。
レビューのみの依頼では所見を返す。仕様の採用・削除は依頼された変更範囲で実施する。
