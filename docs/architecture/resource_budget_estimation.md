## 1. 目的と評価範囲

<!-- traceability: {Resource_Estimation_Model} {Size_20KSLOC} {GLOBAL_StrictMemoryLimit} {ConsolidatedHeap} {ROMParsing} {META_ZeroCostAbstraction} -->
本書は、ランタイムのメモリ使用量と組み込みC++実装のROM / RAM予算を整理する。
資源予算の正本として、測定できた使用量と対象実装で確定すべき配置を区別する。
要求上の容量条件は [`requirement_list.md`](docs/requires/requirement_list.md) に従う。

本書の容量比較では21KBを21,504バイト、32KBを32,768バイトとして扱う。
静的予約量と実使用量の両方を対象実装で確認する。

コード行数、ホストELFセクション、JITコンパイラの静的stack使用量も同日に測定した。

## 2. ランタイムアリーナの計測方法

<!-- traceability: {Runtime_BumpAllocator} {META_BumpAllocator} {Resource_Estimation_Model} -->
ランタイムが所有するアリーナをLoaderとInterpreterへ共有する。
ロード後、インスタンス生成後、各呼出し後に `BumpAllocator.offset` を取得する。
使用量には確保した領域とアラインメントによる空きを含める。
`release` はワークスペースを再利用可能にするが、使用量を減らさない。
したがって、呼出し後の値には解放済みワークスペースの予約量も残る。
今回の成功経路では使用量が単調増加するため、最後の値が観測した最大使用量となる。

| アリーナへ計上する対象 | 計上方法 |
| :--- | :--- |
| 型、関数、インポート、エクスポート、グローバル変数、テーブルの記述情報 | Loaderがレコード件数と参照レイアウトの単価から確保する |
| 関数型索引、局所変数型、局所変数幅の索引 | Loaderが配列とビット列の必要量を確保する |
| 基本ブロック、検索索引、絞込み索引 | Loaderが解析したモジュールに対応する領域を確保する |
| 実体のグローバル変数と関数テーブル | インスタンス生成時に確保する |
| ネイティブ実行用のモジュール、関数、型、テーブルの参照構造 | 初回実行時にホストABIの構造体サイズから確保する |
| 実行コンテキスト、値スタック、局所変数スタック、呼出し情報、制御情報 | 呼出しワークスペースを確保し、後続呼出しで再利用する |
| JIT dispatch用のtrace記述、実行履歴 | モジュールごとの有界ワークスペースを確保し、更新時に再利用する |

Loaderの単価は32ビット対象を想定した参照レイアウトである。
ネイティブ構造体の単価はx86_64上の `ctypes.sizeof` である。
今回の数値は両者を組み合わせた現行アリーナの計上値である。
アリーナは計上モデルであり、Pythonオブジェクトや各ネイティブ配列を一つの物理領域へ配置しているわけではない。
この値をPythonプロセスの実メモリ使用量やARMv8-Mの確定使用量として扱わない。

再現コマンドは次のとおりである。

```bash
uv run python experiments/pysim/benchmarks/memory/bench_runtime_memory.py \
  --calls 3 --output /tmp/fireball-runtime-memory.json
```

各入力について `NativeInterpreter` 単独とHybrid JITを別アリーナで3回ずつ実行する。
計測は戻り値の一致と出力バイト列の一致を検証する。
WASIを使わない入力の戻り値はWasmtimeとも照合する。
AO-Benchでは出力長528バイトを検証する。
各入力の2回目と3回目のアリーナ使用量は同じであった。
確保量とアラインメントの空きの合計は、最終使用量と一致した。
Hybrid JITは全4入力で生成したtraceを実行した。
この観測は指定入力の3回の呼出しに対する結果である。
複数の中断コンテキストや全容量の組合せに対する上限証明は含まない。

## 3. ランタイムメモリの再見積もり結果

<!-- traceability: {Resource_Estimation_Model} {Runtime_BumpAllocator} {JIT_MultiBuffer_Cache} {GLOBAL_StrictMemoryLimit} -->
測定環境はx86_64、ポインタ幅8バイトである。
表の数値はバイト単位である。
全4入力でロード時とインスタンス生成時の計上値は実行方式によらず同じであった。

| 入力 | 関数数 / 基本ブロック数 | ロード後 | インスタンス生成後 | `NativeInterpreter` 最大使用量 | Hybrid JIT最大使用量 | アリーナ外の線形メモリ |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 算術ループ（1,000反復） | 1 / 4 | 276 | 276 | 5,704 | 6,088 | 0 |
| 間接呼出し（100反復） | 4 / 12 | 720 | 724 | 6,384 | 7,280 | 0 |
| 複合カーネル（`k_crc32(1)`） | 28 / 519 | 18,652 | 18,700 | 26,112 | 32,384 | 65,536 |
| AO-Bench（32×16） | 7 / 88 | 3,336 | 3,336 | 9,256 | 15,016 | 65,536 |

実行コンテキストのワークスペースは各入力とも5,252バイトであった。
Hybrid JITのdispatchワークスペースは、trace記述表と履歴32件×4バイトからなる。
現行x64のtrace記述は実行回数カウンタの非所有ポインタを含み、1件64バイトである。
候補マスクは既存のTrackable Maskを借用するため、候補PC配列を計上しない。
trace記述枠は `min(ロード済み基本ブロック数, 3×JIT_CACHE_BANK_ENTRY_CAPACITY)` とする。
x64参照構成の記述枠上限は1バンク32件、3面96件である。
この値はRAM予算の設定値であり、生成コードの平均サイズから導出した値ではない。
記述枠またはコードバイト数の上限に達すると、既存のローテーションを行う。

| 入力 | trace記述枠 | dispatchワークスペース | RAM削減前の測定との差 |
| :--- | ---: | ---: | ---: |
| 算術ループ | 4×64 | 384 | −18,120 |
| 間接呼出し | 12×64 | 896 | −17,608 |
| 複合カーネル | 96×64 | 6,272 | −12,232 |
| AO-Bench | 88×64 | 5,760 | −12,744 |

RAM削減前の測定結果は [`runtime_memory_20261005.json`](experiments/pysim/benchmarks/results/runtime_memory_20261005.json) に保存する。
そのdispatchワークスペースは全入力で18,504バイトであった。

物理ヘッダは、JITコードから相対参照しやすいコード近傍に配置する。
x64ではchain/helper targetだけを保持する16バイトの配置とする。
先頭PC、コード長、昇格状態と未使用variant欄を物理ヘッダに複製しない。
3回目の実行後に常駐するtraceの平均長は、入力順に74、67、93.75、約69.06バイトであった。
この値はヘッダを含む実測値である。
既定コンストラクタ値64バイトを固定生成長または一般的な平均値として扱わない。
この常駐標本から計算した1バンクの目安は約27、30、21、29件となる。
短いtraceの集中時は、コード領域より先に記述枠が満杯になる場合がある。
その場合のキャッシュヒット率と時間への影響は、本メモリ計測では評価していない。

アリーナのアラインメントによる空きは、入力ごとに8、14、50、7バイトであった。
これらの値は表の最大使用量に含む。

JITの実行コード領域8,192バイトはアリーナの外にある。
この領域は共通コード2,048バイトと3バンク×2,048バイトからなる。
アロケータのワークスペース管理表は、現行ホストで1,344バイトである。
64件のオフセット、サイズ、アラインメント、状態の配列から算出した。
アリーナ外のJIT管理情報のうち、物理バッファとして測れる部分を追加計上する。
ビット表は実ストレージのバイト長から計上する。
検索配列はネイティブストレージのサイズから計上する。
アリーナへ登録済みの配列は重複計上しない。
実行回数カウンタは3回目の呼出し後に常駐するtraceの実体を計上する。
表の値は配列とカウンタのpayloadであり、Python管理オブジェクトや配置時の空きを含まない。

| 入力 | カード状態2bit | 候補マスク1bit | 更新索引1bit | ネイティブ検索配列 | 常駐traceカウンタ | 追加計上量 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 算術ループ | 3 | 2 | 2 | 208 | 12 | 227 |
| 間接呼出し | 8 | 4 | 4 | 208 | 8 | 232 |
| 複合カーネル | 912 | 456 | 456 | 208 | 16 | 2,048 |
| AO-Bench | 60 | 30 | 30 | 208 | 124 | 452 |

検索配列は16件の32bitキー、64bitハンドル、8bit使用状態からなる。
カウンタは常駐traceあたり4バイトである。
96件常駐時のカウンタpayloadは384バイトとなる。
この上限値と、入力別の常駐件数による測定値を区別する。

アリーナ、管理表、線形メモリ、JIT実行コード領域、上記payloadを足した既知部分は次のとおりである。
アリーナは観測した最大使用量を使う。
JIT管理payloadは3回目の呼出し後の状態を使う。
コンパイラの一時領域と未確定の管理レイアウトはこの表に含まない。

| 入力 | `NativeInterpreter` の既知部分 | Hybrid JITの既知部分 | Hybridの既知部分を32,768バイトから引いた値 |
| :--- | ---: | ---: | ---: |
| 算術ループ | 7,048 | 15,851 | 16,917 |
| 間接呼出し | 7,728 | 17,048 | 15,720 |
| 複合カーネル | 92,992 | 109,504 | −76,736 |
| AO-Bench | 76,136 | 90,540 | −57,772 |

算術ループと間接呼出しのHybrid JITの既知部分は32,768バイトを下回る。
右端の値は未計上領域へ使える算術上の上限であり、確定した空き容量ではない。
未計上のJIT管理情報とシステム共有領域が残るため、全体RAM適合とは判定しない。
アリーナの実使用量と、要求の静的合計21,504バイトは計測対象が異なる。
静的予約量の適合をこの表の大小だけで判定しない。
線形メモリを1ページ持つ2入力は、その領域だけで最小構成のRAMを上回る。
この2入力をそのまま最小構成で実行する容量適合は成立しない。
ARMv8-M移植時には対象ABIのサイズと構成容量で再計上する。
小さい入力の結果だけから、全構成で32KBに収まるとは判定しない。

## 4. アリーナ外の領域と物理配置の残作業

<!-- traceability: {Resource_Estimation_Model} {ConsolidatedHeap} {GLOBAL_StrictMemoryLimit} {ROMParsing} -->
全体RAMは、各ランタイムのアリーナ予約量、線形メモリ、JIT領域、その他の専有領域に共有領域を加えて見積もる。
第3節に含めたスタックやモジュール記述情報を再度足してはならない。
アリーナ外の主な領域は次のとおりである。

- アロケータのワークスペース管理表1,344バイトは第3節の既知部分に含む。Python管理オブジェクトのサイズは含まない。
- JITのカード状態、候補マスク、更新索引、検索配列、常駐カウンタのpayloadは第3節に含む。
- 履歴リング、コンパイル待ち、バンク索引、chainの流入索引、trace管理レコードの対象ABIレイアウトは未計上である。
- コンパイラの一時領域は第5節に記録する。第3節の実行時の既知部分へ重ねて計上する。
- システムのTCB、IPC、共有ヒープ、ドライバ、ロガー、デバッガの領域は構成ごとに計上する。
- ネイティブの機械スタック、OSと割込みのstack、MPU境界による空きは対象実装で計上する。
- WASMバイナリをROMから参照する場合、そのバイナリの容量はROM側へ計上する。現行測定の入力バイト列はPythonが所有するため、物理的なROM配置の証明にはならない。

`FB_CONF_RUNTIME_BUMP_ARENA_BYTES` の既定値131,072バイトは計上上限である。
この値は各入力の実使用量ではない。
同容量を実機で予約する構成は、アリーナだけで最小構成のRAMを上回る。
実機の予約容量は対象入力、同時実行数、構成容量と対象ABIに基づいて決める。
今回のアリーナ使用量は確定した測定結果として扱う。
対象ボード、ARMv8-M ABI、JIT命令生成、メモリ保護方式、リンカ配置は未確定である。
ROMの `.text` / `.rodata` とRAMの `.data` / `.bss` の全体適合は、対象実装のリンク結果で判定する。

## 5. JITコンパイル時のRAM予算

<!-- traceability: {Resource_Estimation_Model} {GLOBAL_StrictMemoryLimit} {JIT_CopyAndPatch} -->
現行x64コンパイラの一時領域はバンプアロケータへ登録されていない。
コンパイル中には次の配列が同時に存在する。

| 対象 | 容量と単価 | payload |
| :--- | :--- | ---: |
| WASMから復号する命令配列 | 8,192件×16バイト | 131,072 |
| コード生成中のbody配列 | 8,192件×1バイト | 8,192 |
| stack位置の作業配列 | 8,192件×4バイト | 32,768 |
| 呼出し側の出力バッファ | 8,192件×1バイト | 8,192 |
| **配列payload合計** | | **180,224** |

`fb_jit_compile_wasm_trace` は命令配列を生存させたまま `fb_jit_compile_trace` を呼ぶ。
後者はbody配列とstack位置配列を含むbuilderを保持する。
呼出し側の出力バッファも両関数の実行中に生存する。
ABI引数や管理フィールドを含めると、配列payloadより使用量が増える。

Clang 18 / x86_64 / `-O2 -fPIC -fstack-usage` で静的frame使用量を測定した。
設定値は既存のネイティブビルドと同じ値を使う。

| 測定対象 | バイト数 |
| :--- | ---: |
| `fb_jit_compile_wasm_trace` のframe | 131,208 |
| `fb_jit_compile_trace` のframe | 41,096 |
| 同時に生存する2 frameの小計 | 172,304 |
| 呼出し側出力バッファを含む既知部分 | 180,496 |

180,496バイトはコンパイル経路全体の上限ではない。
他のcallee、FFI、結果構造体、Python管理情報を含まない。
このコンパイル時の既知部分だけで、最小構成32,768バイトを147,728バイト上回る。
現行x64コンパイラを同じ配列容量のまま最小構成へ移す容量適合は成立しない。
コンパイル対象の件数、出力長、stack深度に対応する作業領域の設計が残る。
本更新ではコンパイラの確保方法や容量を変更していない。

## 6. ROM予算の更新

<!-- traceability: {Resource_Estimation_Model} {ROMParsing} {JIT_CopyAndPatch} -->
最小構成のROM上限96KBは98,304バイト、想定構成の128KBは131,072バイトとする。
現行x64参照ライブラリを既存ビルドスクリプトで再生成した。
GNU `size -A` でELFセクションを測定した。

| x64参照ライブラリ | `.text` | `.rodata` | 両者の合計 | `.data` + `.bss` | unwind情報 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| C++ Interpreter | 151,442 | 3,056 | 154,498 | 16 | 31,748 |
| x64 trace compiler | 8,433 | 736 | 9,169 | 16 | 624 |
| native fast cache | 755 | 0 | 755 | 16 | 260 |
| **合計** | **160,630** | **3,792** | **164,422** | **48** | **32,632** |

`.text` と `.rodata` の合計は約160.57KiBである。
この値は3つの参照ライブラリに対する値である。
Interpreterの統計・計測・デバッグ用の複数入口を含む。
Python側のLoader、Runtime、JIT管理、システム共有機能をC++へ移す分は含まない。
ホスト共有ライブラリの再配置、GOT、動的リンク情報、debug情報は別セクションである。
unwind情報は `.eh_frame` と `.eh_frame_hdr` の合計を別欄へ示す。
`.data` の初期値は対象firmwareではROMのload imageにも計上する。
`.bss` はRAMへ計上し、ROMのpayloadには足さない。
これらのホスト値をARMv8-Mの命令サイズやROM予測値へ換算しない。

WASM入力をROMへそのまま置く場合の容量は入力バイト長から求める。

| 入力 | WASMバイト長 | 98,304バイトからWASMだけを引いた値 |
| :--- | ---: | ---: |
| 算術ループ | 83 | 98,221 |
| 間接呼出し | 337 | 97,967 |
| 複合カーネル | 15,316 | 82,988 |
| AO-Bench | 1,441 | 96,863 |

右端はfirmware、定数、初期化データ、辞書、配置時の空きへ使える上限である。
複数モジュールを同時にROMへ置く場合は、その全容量を引く。
ARMv8-M firmwareの実使用量と全体適合は未判定である。
対象ABI、機能構成、コンパイラ設定とリンカ配置を確定し、mapとセクションで再計上する。

## 7. 実装規模の更新

<!-- traceability: {Size_20KSLOC} {Resource_Estimation_Model} -->
Python Interpreterは動作比較用の参照実装であり、コード規模予算の計上対象から除外する。
対象はPythonの [`interpreter.py`](experiments/pysim/tier2_runtime/interpreter/interpreter.py) を含むInterpreter配下の4ファイルである。
除外した参照実装は6,305物理行、5,213 SLOCである。
C++ Interpreterはネイティブ実装として計上する。
PythonとC++のInterpreterを重複計上しない。

除外後のpysim Pythonコードは76ファイル、18,778物理行、14,549 SLOCである。
各Tier以下の `.py` と共通入口の `system.py`、`__init__.py` を対象とした。
物理行数は空行とコメントを含む。
Python Interpreter、QA、ベンチマーク、シナリオ、`main.py`、`aobench.py` は集計へ含めない。
ネイティブ実装の `.cxx` / `.hxx` はこの集計に含めない。

SLOCは空行、コメント、Python docstringを除いた物理コード行数とする。
PythonはASTでdocstringを識別し、tokenizeでコメントを除外する。
C/C++はPygmentsの字句解析でコメントを除外する。
プリプロセッサ指令と文字列中のコメント記号はコードとして数える。
計測器の版とファイルごとのハッシュを結果に保存する。

| 対象 | Pythonファイル数 | 物理行数 | SLOC |
| :--- | ---: | ---: | ---: |
| Tier 1 Core | 8 | 2,875 | 2,149 |
| Tier 1 Interface | 3 | 877 | 599 |
| Tier 2 Runtime（Python Interpreter除外） | 33 | 9,015 | 7,135 |
| Tier 3 Plugins | 15 | 3,702 | 2,931 |
| Tier 3 Platform | 15 | 1,503 | 1,091 |
| 共通入口 | 2 | 806 | 644 |
| **合計** | **76** | **18,778** | **14,549** |

| C/C++の対象 | ファイル数 | 物理行数 | SLOC |
| :--- | ---: | ---: | ---: |
| 製品側の `src/` と `inc/` | 8 | 6,410 | 3,781 |
| pysimのnative実装とネイティブABIヘッダ | 9 | 4,287 | 3,924 |
| **現存C/C++合計** | **17** | **10,697** | **7,705** |

製品側には [`malloc.c`](src/allocator/malloc.c) の3,581 SLOCを含む。
`third_party/`、QA、コンセプトコード、形式モデル、ベンチマーク、シナリオは含めない。
Python Interpreter除外後のPythonとnative C/C++の合計は18,473 SLOCである。
これは移植対象の検討に使う現存ソースの集計である。
言語の異なる現存ソースの合計を、完成時の組み込みC++規模とは扱わない。
Python Interpreterを含めた旧合計23,686 SLOCによる予算超過の判定は取り下げる。

要求の20 KSLOCはコメントとテストを除くシステム全域の製品ソースの上限である。
現存C/C++をすべて採用する比較では、20,000 SLOCまでの増分枠は12,295 SLOCとなる。
この枠にはC++未実装のLoader、Runtime、システム共有機能とARMv8-M対応を収める必要がある。
Python Interpreterの測定値は除外記録として保存し、予算の集計へ足さない。
両者の単純合計やPython物理行数の移行係数から、完成時のC++規模を外挿しない。
旧係数による約21.5〜23.4 KSLOCは現行の予算判断に使わない。
完成時のコード規模適合は、対象構成を揃えたC++の実装・計測で判定する。

再現コマンドは次のとおりである。

```bash
bash experiments/pysim/native/tier2_runtime/interpreter/build_native.sh
bash experiments/pysim/native/tier3_plugins/jit/build_native.sh
uv run python experiments/pysim/benchmarks/memory/bench_resource_inventory.py \
  --output /tmp/fireball-resource-inventory.json
```

計測にはClang、GNU `size` とPygmentsを使う。
コード行数だけでROMの機械語サイズやRAM容量を推定しない。
