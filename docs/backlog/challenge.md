# 設計の交差点 (Challenges)

Fireballの開発において、複数の制約や要件が衝突し、慎重なトレードオフ検討が必要な設計項目を管理する。

## 1. 割り込みハンドラによる実行コンテキストの安全性確保 `{Challenge_InterruptSafety}`

### 概要
割り込みハンドラがメイン処理（WASM実行コンテキスト）の文脈を破壊せず、かつ低レイテンシでイベントを通知するための設計。

### 交差点
- **安全性**: 割り込みハンドラがタスクのスタックやレジスタを直接操作するのは危険。
- **リアルタイム性**: Poll方式（`co_yield` 後のチェック）では、次のYieldポイントまでイベント処理が遅延する。
- **実装コスト**: JITコード内に割り込みチェックを動的に挿入（スキャン）すると、実行パフォーマンスが低下する。

### 現在の方針 (2026-01-21)
- 割り込みハンドラは「フラグ書き込み」のみに限定する。 `{TaskPollInterruptFlag}`
- メイン処理は `co_yield` 再開時にフラグをチェックする。
- **検討課題**: JITスキャンやスタック分離による、より強固な隔離機構の必要性。

## 2. 極小RAM環境 (64KB) におけるJITキャッシュ効率の最大化 `{Challenge_JITCacheEfficiency}`

### 概要
限られたRAM領域で、コンパイルコストを抑えつつ、実行速度を維持するためのキャッシュ管理戦略。

### 交差点
- **メモリ制約**: JITキャッシュに割けるメモリは極めて少ない。
- **パフォーマンス**: キャッシュミスが頻発すると、コンパイルオーバーヘッドが無視できなくなる。
- **複雑性**: 高度なLRUやプロファイラは、それ自体がメモリとコードサイズを消費する。

### 現在の方針 (2026-01-21)
- **Active/Old ダブルバッファ**: キャッシュを2分割し、コピーGCベースの単純な入れ替えを行う。 `{JIT_DoubleBuffer_Cache}`
- **遅延ホットスポット検知**: 実行中は履歴記録のみを行い、`co_yield` 時に一括判定する。
- **検討課題**: ホットスポット検知の履歴バッファサイズ（現在は128エントリ）の妥当性評価。
- **検討課題**: カードビットマップの状態管理ビット数（2-bit vs 4-bit vs 8-bit）と、メモリ効率・アクセス速度のトレードオフ。

## 3. 決定論的挙動とパフォーマンスのトレードオフ (概算Yield) `{Challenge_ApproximateYield}`

### 概要
ハードウェアタイマを使わずに、トレース数ベースで実行時間を制御する設計の妥当性。

### 交差点
- **シンプルさ**: タイマ割り込みを使わないことで、カーネルとHALを極限まで単純化できる。
- **正確性**: WASM命令の種類によって実行時間が異なるため、トレース数ベースでは300usecの目標から逸脱する可能性がある。
- **デバッグ性**: 逸脱をどう検知し、設計者にフィードバックするか。

### 現在の方針 (2026-01-21)
- パフォーマンス優先で概算方式を採用。
- 開発フェーズではログ出力による逸脱検知を行う。
- **検討課題**: ランタイムAPI（C++実装部）の実行時間が概算を大きく狂わせるリスクへの対策。

## 4. デバッガ (RSP) バッファとシステムリソースの競合 `{Challenge_DebuggerResource}`

### 概要
GDB接続を維持するためのリソース確保と、ゲストアプリケーションの実行領域の確保の両立。

### 交差点
- **互換性**: VSCode等のモダンなデバッガフロントエンドは、大きなパケットバッファ（2KB〜）を要求する。
- **メモリ制約**: 64KB RAMにおいて2KBは無視できないサイズである。

### 現在の方針 (2026-01-21)
- デバッガ有効時のみ動的にバッファを確保する。
- `qSupported` 等で機能を最小限に絞り、クライアント側を基本コマンドにフォールバックさせる。
- **検討課題**: バッファ不足時のパケット分割送信の実装コスト。
