# 設計雑談メモ (2026-01-21)

設計者との「社会性フィルタなし」の雑談を通じて合意・深掘りされた設計の急所。

## 1. 割り込みハンドラのガード設計
- **現状の懸念**: 割り込みハンドラがメイン処理の文脈を破壊するリスク。
- **合意事項**: 
    - 割り込みハンドラは「フラグ書き込み（タスク固有ヒープへのイベント通知）」のみに限定する。
    - メイン処理との同期は、`co_yield` 後の再開時にメイン側でフラグをチェックする方式（Poll方式）を基本とする。
    - 実装レベルでのガード（JITスキャンやスタック分離）は今後の検討課題。

## 2. 概算Yield (300usec) の運用
- **現状の懸念**: トレース数ベースの概算による時間超過。
- **合意事項**:
    - パフォーマンスとシンプルさを優先し、タイマを使わない概算方式を採用する。
    - 開発フェーズでは、逸脱を検知した際にログを出力することで設計者にフィードバックする。
    - 「削るのが苦しい部分はない」という設計思想に基づき、ランタイムAPIの設計で実行時間を制御する。

## 3. IPCハンドルとCSPの抽象化
- **現状の懸念**: 速度優先でJITパッチ等による直接結合を行うべきか。
- **合意事項**:
    - ハンドルは `co_csp_channel_t*` とし、CSPのセマンティクスを維持する。
    - これにより、システムの透明性（どのタスクが何で待っているか）を確保し、デバッグ性を向上させる。
    - `{COOS_Transparent}` の要件を優先する。

## 4. RAM 64KB制約への対応
- **設計思想**: 「ROMに置けるものはすべてROMに、静的に決まるものはすべて静的に」。
- **IPCメッセージ**: 12個のKey-Value（96バイト）制約は、RAM 64KBからの逆算による必然的な数値。
- **静的DI**: URIマッピングはコンパイル時に解決し、実行時はインデックス配列による二分探索（`IndexedArrayMap`）を用いる。

## 5. JITキャッシュ・コンパイル戦略
- **Active/Old ダブルバッファ**: キャッシュ領域を2つのパーティション（Active/Old）に分割して管理する。
- **コピーGCベースのLRU**: Active領域が一杯になったら、Old領域をクリアして「現在必要なコード」のみを再コンパイルして移す。
- **バッチ・ホットスポット検知**:
    - **履歴バッファ**: 128エントリの履歴を保持。これは中規模ループ（〜60トレース）を2回検知するのに十分なサイズ。
    - **遅延判定**: 実行中は履歴の記録のみを行い、`co_yield` 時のコンテキストスイッチ直前に一括してホットスポット（2回以上出現）を判定・コンパイルする。
    - **メリット**: 実行時の解析オーバーヘッドをゼロにし、スキャンコストと検知能力のバランスを最適化する。
- **Zero Compile Cost**: コンパイルが極めて高速（Copy-and-Patch）であるため、キャッシュミス時の再生成コストを許容し、キャッシュ管理ロジックを極限まで単純化する。

## 6. デバッガ (RSPサーバ) の削ぎ落とし仕様
- **パケットバッファ**: 2KBを確保。VSCode (C/C++拡張) の冗長な要求に耐えるための「必要経費」として割り切る。
- **コマンドセットの最小化**: `vCont` 等の複雑なコマンドは実装せず、`qSupported` で機能を制限することで、クライアント側を `s` (step) / `c` (continue) 等の基本コマンドにフォールバックさせる。
- **メモリ運用**: デバッガ有効時のみランタイムヒープからバッファを確保し、無効時はゲストアプリケーションのリソースとして開放する。
