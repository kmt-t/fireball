# JITコンパイラの理論と構想、見通し

FireballのJITコンパイラは、既存の「最適化重視」のJITとは一線を画し、組み込み環境の制約を「勝利の鍵」へと転換する。

## 1. Zero Compile Cost 定理の具現化 `{JIT_ZeroCompileCostTheorem}`

### 理論の再定義
コンパイルコスト $C_{comp}$ を極限まで下げることで、プロファイルや最適化に費やす時間 $C_{prof} + C_{opt}$ をゼロに近づける。これにより、実行効率の向上 $T_{interp} - T_{jit}$ がわずかであっても、小規模なループ回数 $N$ でトータルの実行時間が短縮される。

### WASMスタックマシンの既知の最適化の活用
WASMバイナリは生成時にすでにスタックマシンとして最適化されており、計算の依存関係はスタックの順序に反映されている。
- **手抜きの正当性**: 複雑なレジスタ割り当てアルゴリズムを実装せず、スタックトップ付近の数エントリを物理レジスタに固定するだけで、WASMが本来持つ最適化の恩恵をネイティブ速度で引き出せる。 `{JIT_RegisterMapping}`
- **Copy-and-Patch**: 命令テンプレートを連結し、即値や分岐先をパッチするだけの「最短経路」を採用する。 `{JIT_CopyAndPatch}`

## 2. 生存戦略：Active/Old ダブルバッファ `{JIT_DoubleBuffer_Cache}`

### 世代管理によるスラッシング抑制
RAM 64KBという極限環境では、JITキャッシュを大きく取れない。
- **2パーティション管理**: キャッシュを Active と Old に分割（各2KB等）し、Activeが一杯になった際に Old をクリアしてスワップする。
- **シミュレーション結果**: ワーキングセットがパーティションサイズを25%超過しても、75%以上のヒット率を維持できることが証明されている。 `{SimpleJITArchitecture}`

### バッチ・ホットスポット検知 `{SimpleJITArchitecture}`
- **128エントリ履歴バッファ**: 中規模ループを確実に捉えつつ、スキャンコストを抑えたサイズ。
- **遅延バッチ判定**: `co_yield` 時のコンテキストスイッチ直前に一括判定を行うことで、実行時の解析オーバーヘッドをゼロにする。
- **反射的JIT**: 一般的なプロファイラのような数千回の実行待機を排除し、2回出現で即座にJIT化する。これは $C_{comp} \approx 0$ であるからこそ許容される「手数」の戦略である。

### 一般的なプロファイラとの比較
| 項目 | 一般的なプロファイラ | Fireball バッチ検知 |
| :--- | :--- | :--- |
| メモリ消費 | 大（全ブロックにカウンタ） | 極小（128エントリ固定） |
| 検知速度 | 遅い（確信を待つ） | 極めて速い（反射的） |
| 実行負荷 | 中（分岐ごとの演算） | ゼロ（ID記録のみ） |

### スケールアップ考察：vs Google V8 (Browser Use Case)
Fireballの設計をブラウザ級にスケールさせた場合、V8（Ignition/Turbofan）と比較して以下の極端な特性を持つ。

- **ピーク性能**: V8が有利だが、Fireballも肉薄する。Fireballはインライン展開を行わないが、**全関数を分岐予測が効きやすい形式で生成する**ため、ハードウェアの恩恵を最大限に引き出し、関数呼び出しのオーバーヘッドを最小化する。
- **応答性・起動速度**: Fireballが圧倒。V8がプロファイリングと最適化に悩む間に、Fireballは最初からネイティブ速度で処理を終える。
- **リソース効率**: Fireballが圧倒。V8が数百MBを要するシーンを、Fireballは数MBのJITキャッシュのみでこなす可能性がある。

## 3. 結論
FireballのJITは、JIT研究の王道である「賢さ」を捨て、組み込みの現実に即した「素早さ」と「潔さ」を選んだ。この戦略により、WAMRが到達できない「省メモリと高パフォーマンスの両立」を実現する。
