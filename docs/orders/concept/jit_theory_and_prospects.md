# JITコンパイラの理論と構想、見通し

FireballのJITコンパイラは、既存の「最適化重視」のJITとは異なる方向性を取り、組み込み環境の制約を設計上の前提として丁寧に活かす。

## 1. Zero Compile Cost 定理の具現化 `{JIT_ZeroCompileCostTheorem}`

### 理論の再定義
コンパイルコスト $C_{comp}$ を極小化することで、プロファイルや最適化に費やす時間 $C_{prof} + C_{opt}$ を実質的に抑える。これにより、実行効率の向上 $T_{interp} - T_{jit}$ がわずかであっても、小規模なループ回数 $N$ でトータルの実行時間が短縮される可能性が高まる。

### WASMスタックマシンの既知の最適化の活用
WASMバイナリは生成時にすでにスタックマシンとして最適化されており、計算の依存関係はスタックの順序に反映されている。
- **簡略化の妥当性**: 複雑なレジスタ割り当てアルゴリズムを実装せず、スタックトップ付近の数エントリを物理レジスタに固定するだけで、WASMが本来持つ最適化の恩恵を実行性能に反映しやすい。 `{JIT_RegisterMapping}`
- **Copy-and-Patch**: 命令テンプレートを連結し、即値や分岐先をパッチするだけの「最短経路」を採用する。 `{JIT_CopyAndPatch}`

## 2. 生存戦略：Active/Old ダブルバッファ `{JIT_DoubleBuffer_Cache}`

### 世代管理によるスラッシング抑制
RAM 64KBという制約下では、JITキャッシュを大きく取れない。
- **2パーティション管理**: キャッシュを Active と Old に分割（各2KB等）し、Activeが一杯になった際に Old をクリアしてスワップする。
- **シミュレーション結果**: ワーキングセットがパーティションサイズを25%超過しても、75%以上のヒット率を維持できる可能性が示されている。 `{SimpleJITArchitecture}`

### バッチ・ホットスポット検知 `{SimpleJITArchitecture}`
- **128エントリ履歴バッファ**: 中規模ループを捉えつつ、スキャンコストを抑えたサイズ。
- **2-bit状態ビットマップ**: 1024カードを2-bitで管理し、未実行/1回/Hotの状態遷移で低コストに判定する。
- **遅延バッチ判定**: `co_yield` 時のコンテキストスイッチ直前に一括判定を行うことで、実行時の解析オーバーヘッドを抑える。
- **反射的JIT**: 一般的なプロファイラのような数千回の実行待機を避け、2回出現で即座にJIT化する。これは $C_{comp} \approx 0$ を前提とした「手数」の戦略である。

### 一般的なプロファイラとの比較
| 項目 | 一般的なプロファイラ | Fireball バッチ検知 |
| :--- | :--- | :--- |
| メモリ消費 | 大（全ブロックにカウンタ） | 小（128エントリ固定） |
| 検知速度 | 遅い（確信を待つ） | 速い（反射的） |
| 実行負荷 | 中（分岐ごとの演算） | 低（ID記録中心） |

### スケールアップ考察：vs Google V8 (Browser Use Case)
Fireballの設計をブラウザ級にスケールさせた場合、V8（Ignition/Turbofan）と比較して以下のような特性が見込まれる。

- **ピーク性能**: V8が有利だが、Fireballも一定の性能に近づく可能性がある。Fireballはインライン展開を行わないが、**全関数を分岐予測が効きやすい形式で生成する**ことで、ハードウェアの恩恵を引き出し、関数呼び出しのオーバーヘッドを抑える。
- **応答性・起動速度**: Fireballが優位になりやすい。V8がプロファイリングと最適化に時間を要する間に、Fireballは早期にJIT結果を反映できる。
- **リソース効率**: Fireballが優位になる見込み。V8が数百MBを要するシーンを、Fireballは数MBのJITキャッシュのみで処理できる可能性がある。

## 3. 結論
FireballのJITは、JIT研究の王道である「賢さ」よりも、組み込みの現実に即した「素早さ」と「簡潔さ」を重視する。この戦略により、WAMRが到達しにくい「省メモリと高パフォーマンスの両立」に近づける。
