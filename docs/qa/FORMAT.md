# テスト仕様書フォーマット

このフォーマットは、`docs/qa/tier*/` および `docs/qa/specs/` に置く `*_test_spec.md` に適用する。テスト仕様書は、対応する設計正本から導出した検証条件と期待結果を定義する。実行結果や実装コードの正本を置き換えない。

テスト仕様書は、次の4つのトップレベルセクションをこの順序で持つ。テストケースを分類する見出し、直交表、形式検証の確認項目、GOTCHA一覧は `## 2. テストケース一覧` の下位見出しとして配置する。

## 1. 目的と対象範囲

対応するコンポーネント設計書を「正本」としてリンクする。参考実装や形式検証モデルを使用する場合は、実在するファイルをリンクする。検証対象と対象外の境界を本文で定義する。

## 2. テストケース一覧

テストケースは表で定義する。通常のテストケースには、次の列を使用する。

| テストケースID | 検証項目 | 前提条件 | 手順 | 期待結果 | 紐付け |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `TEST-<COMPONENT>-<番号>` | 検証する振る舞い | 成立条件 | 実行手順 | 観測可能な結果 | 設計正本・キーワード・実装 |

直交表を用いる場合は、テストケース表より前に因子と水準を示す。GOTCHAや形式検証の確認項目を記載する場合は、テストケースIDと区別できるID列を使用する。

各ケースは、前提条件、手順、期待結果を分離して記述する。期待結果は、実装の現在値ではなく設計正本から独立に導出する。未実装のケースは、未実装であることと検証予定の範囲を明記する。

## 3. テスト検証実績と網羅状況

仕様として定義したケースの範囲と、実行済みケースの範囲を分けて記載する。実行結果を記載する場合は、実行日、対象ソース、テストスイート、コマンド、環境、成功・失敗・skipの件数、および未実行理由を示す。実行していない結果を合格として記載しない。

## 4. 未検証・スコープ外

未検証の条件、対象外の機能、実機依存の条件、および別のテスト仕様書が正本となる範囲を列挙する。対象外の理由と参照先を示し、未検証を暗黙に残さない。

`README.md`、結合テストシナリオ、検証因子マトリクス、実行結果、バグ記録は、それぞれの資料の役割に応じた構成を持つ。本フォーマットをそれらへ機械的に適用しない。
