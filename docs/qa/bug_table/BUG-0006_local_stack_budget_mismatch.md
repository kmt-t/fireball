# BUG-0006 ローカル値領域の容量が予算資料と食い違う

| 項目 | 内容 |
| :--- | :--- |
| 重大度 | 中 |
| 状態 | 要確認 |
| 対象 | `interpreter`, [`resource_budget_estimation.md`](docs/architecture/resource_budget_estimation.md) |
| 発見日 | 2026-09-19 |

## 1. 食い違いの内容

予算資料と実装で、ローカル値領域の容量が一致しない。

| 出典 | 記載 |
| :--- | :--- |
| 予算資料（インタープリタ統合スタックの内訳） | `ローカル値領域` は768バイト（192ワード相当） |
| pysim（`NATIVE_VALUE_STACK_CAPACITY`） | 128ワード。1ワードは32ビットである |

実測したレコードの大きさは、`ValueStackNative` が520バイトである（値512バイトと、サイズ等の8バイト）。実装の値領域は512バイトであり、予算資料の768バイトより256バイト小さい。

オペランドスタックも同様である。予算資料は1KBとするが、pysimの容量は64ワード（256バイト）である。

## 2. 訂正

この不具合の初版は、次のとおり誤っていた。

- 「128スロット×1スロット8バイト＝1,024バイト」と記録した。容量の128は、スロット数ではなく、32ビットの生ワード数である。
- 「最大フレームは30スロット」「3段で約90スロット」と記録した。単位は、ローカル数とワード数を取り違えていた。

## 3. 未確認の事項

- 仕様側の768バイトと、実装側の128ワード（512バイト）のどちらが正かは、決まっていない。
- 実装の値領域とオペランドスタックが、予算資料より小さい理由は、確認していない。

## 4. 確認方法

- 予算資料の内訳と、実装の容量のどちらを正とするか決める。
- 決定後に、資料と実装を同一の変更で揃える。

## 5. 実施した設計変更

フレームごとにローカルのスロット幅を切り替える設計を実装した。

- 幅は、フレーム内で最大の変数サイズで決める。i32/f32だけのフレームは4バイト、i64/f64を含むフレームは8バイトである。v128を含む場合は16バイトとする。
- 同一フレーム内で幅を混在させない。
- JITは、関数ごとのスロット幅から、ローカルの変位を計算する。i32のみのフレームに限定しない。
- 幅は、ローカルごとに2ビットのビットマップで保持する。型の配列は保持しない。型はオペコードから決まるためである。
- フレームに必要な情報は、スロット幅のビットマップとスロット語数だけである。
- 検証は、`TEST-INTP-73`、`TEST-INTP-74`、`TEST-JITC-59`、`TEST-JITR-60` である。

この設計変更で、i32/f32だけのフレームは、ローカル値領域の使用量が半分になった。実測では、16個のi32ローカルを持つ再帰関数が、7フレームで112ワードに収まる。f64ローカルを1個加えると、同じ深さで238ワードになり、容量を超える。

容量の食い違い自体は、この設計変更では解決していない。
