# BUG-0009 JITが降ろしを代行した制御フレームが残り、結果が食い違う

| 項目 | 内容 |
| :--- | :--- |
| 重大度 | 重大 |
| 状態 | 修正済み |
| 対象 | `runtime_engine` |
| 発見日 | 2026-09-19 |

## 1. 現象

Tier 3で、実行が終了しても結果がwasmtimeと食い違う。または、実行が終了しない。

## 2. 再現手順

```bash
.venv/Scripts/python.exe experiments/pysim/benchmarks/profile/bench_vtune_workload.py --phase suite_jit --kernel k_text:1
```

修正前の結果は、`k_text` の結果が `0x14de2611` になった。wasmtimeの結果は `0x610d4675` である。

`k_expr` も食い違った。生成した制御フロー（シード17）は、終了しなかった。

## 3. 切り分け

`k_text` の1単位で、次の結果を得た。

| 実行方法 | 結果 |
| :--- | :--- |
| Tier 2（`Interpreter.call`） | 一致 |
| `RuntimeEngine`（JITコンパイラなし） | 一致 |
| `RuntimeEngine`（JITあり、チェインあり） | 食い違い |
| `RuntimeEngine`（JITあり、チェインなし） | 一致 |

コンパイルを許すトレースの集合を二分して、2つのトレース（`0x110198` と `0x1101a8`）の組み合わせが必要であることを確認した。

## 4. 原因

トレースは、`end` や `br` による制御フレームの降ろしを代行しない。そのため、フレームスタックが必要な深さより深いまま残る。

古いフレームの切り詰めは、次の位置がブロック先頭のときにだけ行われていた。次の位置がブロック先頭でない場合は、古いフレームが残ったまま、インタープリタが `br` を実行した。

- ブロック先頭でない位置には、`block`、`loop`、`end` などの構造命令の位置がある。
- ループを抜けた直後の `br 0` の位置も、ブロック先頭ではない。

古いループフレームが最内のフレームに見えるため、`br 0` がループ先頭へ戻った。結果が食い違い、条件によっては無限ループになった。

連結ありの実行では、連結先のブロック先頭での切り詰めも省かれるため、症状が出やすかった。

## 5. 修正

[`runtime_engine.py`](experiments/pysim/tier2_runtime/runtime_engine.py) の `_invoke_trace` で、再開位置を確定する前に、制御フレームを再開位置の深さまで切り詰める。

深さは、次のとおり求める。

- 再開位置がブロック先頭なら、そのブロックが記録する深さを使う。
- 先頭でなければ、開始がその位置より前にあり、対応する `end` がその位置以降にある構造命令の数を、制御マップから数える。

## 6. 検証

- `TEST-JITR-55`（修正前は停止、修正後は通過）と `TEST-JITR-58`（生成した60本）を追加した。
- 修正前の状態で、シード17は `assert` で停止した。
- 全17カーネルの通し実行が、Tier 2と同一のチェックサム（`0xC09373A7`）になった。

## 7. 未確認の事項

トレースの退避（eviction）と昇格（promotion）の後に、ネイティブチェインが正しく再リンクされるかは、専用に検査していない。実行された4,053件のチェインについて、Pythonのメタデータとネイティブのヘッダが一致することは確認した。
