# イベント駆動型グリーンスレッド実装のサーベイ

本ドキュメントは、FireballプロジェクトにおけるOSカーネル設計（COOS）の再検討のため、既存のイベント駆動型軽量タスク・グリーンスレッド実装の設計アプローチを調査・整理したものである。

## 1. 代表的なシステムの比較

| システム | スタック管理 | スケジューリング | 通信モデル | 主な特徴 |
| :--- | :--- | :--- | :--- | :--- |
| **Protothreads** | スタックレス | 協調型 (Cマクロ) | なし | 数バイトのRAMで動作。ローカル変数が保持されない。 |
| **Win16 / Early MacOS** | 独立スタック | 協調型 (メッセージループ) | メッセージ | `GetMessage` / `Yield` ベースの明示的な譲り合い。 |
| **Erlang (BEAM VM)** | 動的スタック | プリエンプティブ (VM) | **CSP (Mailbox)** | 共有なし (Shared Nothing) と強力な隔離。 |
| **QPC (Active Objects)** | 単一または独立 | イベント駆動 (RTC) | **イベント (AO)** | 状態マシンベース。Run-to-Completion 規則。 |
| **Node.js (libuv)** | 単一スタック | イベント駆動 | コールバック | 非ブロッキング I/O と単一ループ。 |

## 2. 各システムの詳細設計

### 2.1 Protothreads (Contiki OS)
*   **設計アプローチ**: C言語の `switch-case` ラベル（Duff's Device）を利用して中断・再開ポイントをエミュレートする。
*   **メリット**: コンテキスト保存のためのスタックを必要とせず、タスクごとに2〜4バイトの整数（継続ポイント）があれば足りる。
*   **Fireballへの示唆**: RAM 32KB環境では非常に強力。ただし、タスクの状態管理をプログラマが明示的に行う必要がある。

### 2.2 Win16 形式
*   **設計アプローチ**: アプリケーションが明示的に `GetMessage` や `PeekMessage` を呼び出して制御をOSに返す。
*   **メリット**: OS側でタイマ割り込みによる複雑なコンテキストスイッチが不要。割り込みがイベントキューに投入されるだけの単純な構造。
*   **Fireballへの示唆**: ユーザーが提案した「Win16的な設計」は、組み込み環境でのデバッグ可能性と電力効率に優れる。

### 2.3 Erlang プロセスモデル
*   **設計アプローチ**: プロセス間は完全に独立（Isolate）しており、メッセージパッシングのみで通信する。
*   **メリット**: 障害の影響が他に波及しない。CSPモデルと非常に相性が良い。
*   **Fireballへの示唆**: メモリ隔離（Memory Isolation）とゼロコピー通信を両立させる際のゴールとなるモデル。

### 2.4 QPC (Active Objects)
*   **設計アプローチ**: 各タスクを「イベントキューを持つ自律的な状態マシン」として扱う。
*   **メリット**: Run-to-Completion (RTC) により、一つのイベント処理中に共有リソースへのアクセス競合が発生しない。
*   **Fireballへの示唆**: コルーチンを使わずに「状態マシン」として設計を記述する手法は、形式検証（TLA+）との相性が最も良い。

## 3. Fireball への適用案

現在のドラフト（`docs/components/os_event_driven.md`）は、以下の要素を組み合わせた独自のバランスを目指している。

1.  **構造**: QPC の Active Object モデル（状態マシンとしてのタスク）。
2.  **通信**: Erlang の CSP モデル（所有権移譲を伴うゼロコピーメッセージ）。
3.  **基盤**: Win16 形式のシンプルなメッセージループ。

これにより、C++コルーチンが持ち込んでいた「隠れたフレームサイズ」や「メモリ管理の不透明さ」を排除し、RAM 32KBでの予測可能な動作を実現する。
