AO-Bench WAMR Fast Interpreter 比較
計測日: 2026-10-06

## 目的

既存の experiments/pysim/benchmarks/aobench/aobench.wasm を同一バイト列のままFireball NativeInterpreterとWAMR Fast Interpreterで実行し、Interpreter同士のホスト上の実行時間を比較する。
標準ベンチマークは32×16だが、この試行では幅・高さを320×180へ拡大した。

## 入力と正当性

- WASM: experiments/pysim/benchmarks/aobench/aobench.wasm
- WASM SHA-256: 9f5dc300e96641bf040551f9f56cb6e5bda084e98bde83a3fb1cff9a719d49e9
- エクスポート関数: main(320, 180)
- 画像出力: 57,780 bytes。各行320文字＋改行、180行。
- Fireball出力SHA-256: 6d04ea80d9a1fd773c85d413057d64797f32dbb257a753d767a378d730d7d699
- WAMRは3プロセス×8フレームをファイルに出力し、全24フレームがFireball出力とバイト単位で一致した。
- ヒット画素数は32,298。固定小数点AOサンプルを4回とし、1フレームあたり186,792 rayと数えた。

## 実行環境

- CPU: AMD Ryzen 5 5500GT、x86_64、計測プロセスをCPU 2へ固定。
- OS: Linux 7.0.0-34-generic。
- Clang: Ubuntu clang 21.1.8。
- Fireball NativeInterpreter共有ライブラリ: 作業ツリーのC++ソースからClang -O2 で再ビルド。
- WAMR: third_party/wasm-micro-runtime、commit f5f57c09aee623436f5fb87a90798fdd2cdf39fd、iwasm 2.4.3。
- WAMR構成: Interpreter/Fast Interpreter/WASIを有効化し、AOT/JIT/Fast JITを無効化。C runtimeはClang -O2 でビルド。

## 計測方法

各プロセスで320×180を1回ウォームアップし、その後7回計測した。これを各エンジンで3プロセス実行した。最終値はプロセスごとの7回中央値の中央値である。

FireballはWASMの解析、System/WASI/Interpreter生成を計測区間から除外し、NativeInterpreter.call()を計時した。stdout sinkには57,780 bytesを収容するStreamTransportを使った。

WAMRはruntime初期化、WASMロード、instantiate、exec environment生成を計測区間から除外し、C APIのwasm_runtime_call_wasm()を計時した。WASI stdoutは一時ファイルへ出力した。

| WAMR Fast Interpreter | 158.921 ms | 152.820 ms | 142.536 ms | 152.820 ms | 1,222,303 rays/s |

この条件ではWAMR Fast Interpreterが7.375倍のスループットだった。

## 適用範囲

この数値は、現行PySIMのNativeInterpreterをPythonホスト/WASI境界から呼び出したx86_64計測値である。Fireballのホスト呼出しはPythonのWASI/HAL経路を通る。WAMRのホスト呼出しはC runtimeのWASI経路を通る。stdout sinkもFireballの固定長メモリバッファとWAMRのファイルで異なるため、完全なInterpreter命令ディスパッチ単体の比較ではない。

計測ハーネスは /tmp/fireball_aobench_runner.py と /tmp/wamr_aobench_runner.c に置いた。WAMR build directoryは /tmp/fireball-wamr-build-clang、WAMR C harnessは /tmp/wamr_aobench_runner にある。

## ビットマップサイズ別計測と線形回帰

同一のaobench.wasmを使い、16:9の5サイズで追加計測した。各サイズ・各エンジンについて、プロセスごとに1回ウォームアップ後7回を計時し、3プロセスの中央値をサイズごとの代表値とした。プロセス実行順は交互に入れ替え、計測プロセスをCPU 2へ固定した。

以下の320×180の値はサイズ掃引で再計測した結果であり、上記の先行する単独320×180計測とは別の実行である。5点回帰にはサイズ掃引の値だけを用いた。

| サイズ | 総ray数/フレーム | Fireball中央値 | WAMR中央値 | Fireball/WAMR | 出力bytes |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 64×36 | 7,332 | 43.386 ms | 7.413 ms | 5.853× | 2,340 |
| 128×72 | 29,732 | 173.310 ms | 23.985 ms | 7.226× | 9,288 |
| 192×108 | 67,032 | 388.410 ms | 50.971 ms | 7.620× | 20,844 |
| 256×144 | 119,352 | 693.829 ms | 90.805 ms | 7.641× | 37,008 |
| 320×180 | 186,792 | 1,071.565 ms | 138.915 ms | 7.714× | 57,780 |

各サイズで両エンジンの画像出力はバイト単位で一致した。ヒット画素数は順に1,257、5,129、11,574、20,622、32,298。

5サイズの代表値を最小二乗法で回帰した結果:

- Fireball: time_ms = 3.259 + 0.0057386 × total_rays（5.739 µs/ray、R²=0.999928）
- WAMR: time_ms = 2.126 + 0.00073484 × total_rays（0.735 µs/ray、R²=0.999880）
- レイ数あたりの傾きの比は約7.81倍。ピクセル数で回帰してもFireball R²=0.999941、WAMR R²=0.999891。

サイズ点では非常に直線性が高いが、これは5点の範囲内での経験的な回帰である。aobenchのレイ数は画面内ヒットに応じて増えるため、他の場面・解像度・出力経路の性能をそのまま予測するものではない。計測生データは /tmp/aobench_wamr_size_sweep_20261006.json に保存した。

## WAMR Fast InterpreterとClassic Interpreterの比較

WAMR 2.4.3の同じソースからFast Interpreter版とClassic Interpreter版をビルドした。Classic InterpreterはSIMD有効構成と併用できないため、差を実行エンジンに揃えるこの比較では両版ともSIMD、AOT、JITを無効化し、WASIを有効化した。Clang 21.1.8のRelease構成を使い、同一のWASMとC harnessを実行した。

各サイズ・各版について、CPU 2へ固定した3プロセスを実行し、各プロセスでウォームアップ1回の後に7回計時した。サイズごとの値は3プロセスの中央値である。

| サイズ | 総ray数/フレーム | Fast中央値 | Classic中央値 | Classic/Fast時間比 |
| ---: | ---: | ---: | ---: | ---: |
| 64×36 | 7,332 | 5.128 ms | 7.753 ms | 1.512× |
| 128×72 | 29,732 | 21.704 ms | 31.854 ms | 1.468× |
| 192×108 | 67,032 | 49.036 ms | 72.012 ms | 1.469× |
| 256×144 | 119,352 | 88.779 ms | 130.869 ms | 1.474× |
| 320×180 | 186,792 | 137.035 ms | 206.244 ms | 1.505× |

全サイズでFast/Classic間の出力フレームがバイト単位で一致した。レイ数に対する線形回帰は次の通り:

- Fast: time_ms = -0.139 + 0.00073707 × total_rays（737.1 ns/ray、R²=0.999892）
- Classic: time_ms = -1.131 + 0.00110761 × total_rays（1,107.6 ns/ray、R²=0.999919）
- 回帰傾きではFastが約1.50倍高いスループットだった。

性能・RSSのプロセス別生データは /tmp/aobench_wamr_classic_fast_size_sweep_20261006.json に保存した。memory profilerは速度計測と分離した専用ビルドで実行した。

## Fireball NativeInterpreterとWAMRの3者比較

Fireball NativeInterpreter、WAMR Classic Interpreter、WAMR Fast Interpreterを同じaobench.wasm、同じ5サイズで再計測した。WAMRは上記と同じくSIMD/AOT/JITを無効化したビルドを使った。全エンジンをCPU 2へ固定し、サイズごとに各エンジン3プロセス、各プロセスでウォームアップ1回後7回を計時した。プロセス実行順はローテーションした。

| サイズ | 総ray数/フレーム | Fireball | WAMR Classic | WAMR Fast | Fireball/Classic | Fireball/Fast |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 64×36 | 7,332 | 44.327 ms | 10.057 ms | 5.270 ms | 4.41× | 8.41× |
| 128×72 | 29,732 | 196.937 ms | 32.642 ms | 24.368 ms | 6.03× | 8.08× |
| 192×108 | 67,032 | 389.383 ms | 73.922 ms | 49.863 ms | 5.27× | 7.81× |
| 256×144 | 119,352 | 733.943 ms | 148.163 ms | 98.444 ms | 4.95× | 7.45× |
| 320×180 | 186,792 | 1,086.670 ms | 198.610 ms | 136.476 ms | 5.47× | 7.96× |

全サイズで3者の画像出力はバイト単位で一致した。5点を総レイ数で回帰した傾きは、Fireballが5,822.7 ns/ray（R²=0.998156）、WAMR Classicが1,088.6 ns/ray（R²=0.987890）、WAMR Fastが743.7 ns/ray（R²=0.992497）だった。傾きで見るとWAMR ClassicはFireballの約5.35倍、WAMR Fastは約7.83倍のスループットだった。サイズごとの実測にはプロセス間の変動があるため、この比率は今回のホスト・実行経路での目安とする。

320×180でのピークRSSは、Fireballが3プロセス中央値27,976 KiB、WAMR Classicが11,060 KiB、WAMR Fastが10,924 KiBだった。Fireballの計測プロセスはPySIMのPythonホストを含み、WAMRはC harnessと静的リンクruntimeのプロセスであるため、このRSS差にはホスト実装の差も含む。

Fireball NativeInterpreter共有ライブラリは188,176 bytes（text 119,183 bytes）。WAMRの静的リンクC harness実行ファイルはClassic 413,088 bytes（text 329,588 bytes）、Fast 436,240 bytes（text 351,900 bytes）。Fireballの値はInterpreter共有ライブラリ単体、WAMRの値はruntimeとC harnessを含む実行ファイルなので、バイナリサイズを同じリンク構成のランタイム同士として直接比較できない。FireballをC++ホストで組み込んだときのプロセスRSSは別計測が必要である。

3者比較のプロセス別生データは /tmp/aobench_fireball_wamr_threeway_20261006.json に保存した。

## Fireballのyieldしきい値による比較差

前節のFireball計測は既定の `FB_CONF_RUNTIME_YIELD_THRESHOLD=64` を使っていた。これはLOOP後方分岐回数のしきい値であり、64回ごとにネイティブdispatchからPythonの `step_native()` 呼出しループへ戻る。既定値は100 MHz Cortex-M33の約300 µs量子を狙う初期値である。

yield頻度の影響を見るため、ソースと製品設定を変更せず、計測用プロセス内だけで同じ定数を `0xFFFFFFFF` に差し替えて再計測した。320×180では別のカウント実行で1フレームあたりの `step_native()` 呼出しが既定値の25,618回から1回へ減り、両条件の出力ハッシュは一致した。WASI等の明示的なホスト関数呼出しは残る。

| サイズ | Fireball threshold=64 | Fireball threshold=max | WAMR Classic | WAMR Fast | 既定 / max |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 64×36 | 54.315 ms | 36.256 ms | 9.281 ms | 5.634 ms | 1.50× |
| 128×72 | 222.492 ms | 142.548 ms | 39.251 ms | 26.301 ms | 1.56× |
| 192×108 | 498.328 ms | 301.638 ms | 87.642 ms | 53.824 ms | 1.65× |
| 256×144 | 844.967 ms | 545.821 ms | 166.118 ms | 100.802 ms | 1.55× |
| 320×180 | 1,266.060 ms | 820.757 ms | 231.623 ms | 156.130 ms | 1.54× |

320×180では大きなyield間隔により実行時間が約35%短縮した。回帰傾きは既定値6,741.6 ns/ray、大きな間隔4,382.8 ns/ray、WAMR Classic 1,262.4 ns/ray、WAMR Fast 837.4 ns/ray。大きな間隔でも今回のC++ host境界込みFireball計測はWAMR Classicより約3.47倍、Fastより約5.23倍多く時間を要した。

この最大しきい値は連続実行時の応答性を外した測定条件であり、製品設定の提案ではない。既定64は協調スケジューリングの時間量子を意図する。VTune/uProfは環境にないため、CPU hotspotのサンプリングは未実施。計測は同一条件の複数プロセスwall-clock比較と、別実行でのdispatch再開回数確認である。

yield感度計測の生データは /tmp/aobench_fireball_yield_wamr_20261006.json に保存した。

## WASI host callをNativeInterpreter内で無効化した比較

WASIホスト関数の処理量とPython境界の影響を分けるため、計測専用のC++ Interpreter buildを作り、import命令をNativeInterpreter内で完結させた。importの引数をpopし、戻り値スロットを0で埋めて次の命令へ進む。Python host functionへ戻らず、stdoutにも出力しない。製品ソースと設定は変更していない。

aobench moduleのfunction importは `wasi_snapshot_preview1.fd_write` のみだった。別実行でWASI通常経路を数えたところ、1フレームにつき `fd_write` は1回で、57,780 bytesを渡した。dummy経路では `main` の戻り値57,780は維持されたが、画像バイト列をhost側で回収・比較していないため、dummy経路を含めた画像一致は確認対象外である。

320×180でCPU 2に固定し、プロセスごとにウォームアップ1回の後7回を計時、3プロセスを実行した。yield=64の通常/dummy比較と、yield=maxでの3経路比較は別の実行群であるため、時間は同じ行の中だけで比較する。

| 経路 | yield | 3プロセス中央値 | transport出力bytes/frame |
| :--- | ---: | ---: | ---: |
| WASI通常 | 64 | 1,274.490 ms | 57,780 |
| C++内import dummy | 64 | 1,204.513 ms | 0 |
| WASI通常 | max | 843.018 ms | 57,780 |
| Python `fd_write` stub（byte数記録のみ） | max | 785.769 ms | 0 |
| C++内import dummy | max | 783.766 ms | 0 |

yield=64ではC++内dummyで5.5%短縮した。yield=maxの3経路比較では、通常のWASI出力を捨てるPython stubで6.8%短縮し、さらにC++内dummyにすると0.25%短縮した。最後の差はプロセス間のばらつきより小さい。今回の解像度では、Python host-call境界をなくす利得は小さく、ほとんどの差は57,780 bytesの出力をtransportへ渡す処理にある。通常経路は1回のhost callなので、この比率をhost call頻度の高い workload に一般化はできない。

通常WASIとPython stubは `fd_write` をPythonで1回実行した。stubはiovec長を合計して `nwritten` に書き、successを返すが、バイト列をtransportへ転送しない。C++内dummyはhost call自体を飛ばし、WASI副作用を実装しない。WASI出力なしの時間だけでInterpreter本体の命令速度を代表させる用途には使えるが、同じ意味論の実行時間ではない。

NativeInterpreter共有ライブラリの比較ビルドでは通常版がtext 119,183 bytes、dummy版が119,567 bytes（+384 bytes）だった。両版のdataは672 bytes、bssは8 bytes。dummy版は計測用の条件付きbuildで、製品フットプリントの提案値ではない。

プロセス別生データは /tmp/aobench_fireball_dummy_host_320_20261006.json と /tmp/aobench_fireball_host_modes_320_20261006.json に保存した。呼出し回数カウントは /tmp/fireball_aobench_wasi_call_counter.py を使った別実行である。
