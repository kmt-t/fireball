## 1. 検出された矛盾・警告 (Issues Found)

### 🟡 WARN: `{META_RestrictedPhysicalAccess}`
- **サマリー**: The implementation of {META_RestrictedPhysicalAccess} is generally consistent across sections, but there is a contradiction regarding the granularity of the permission check (Task-ID based vs. Global Table based).
- **詳細項目**:
  - **[ERROR]** `sec:components/tier1_core/system_syscall.md#5.3. vMMIO Generic vs. sec:components/tier1_core/system_config_details.md#物理アクセス許可範囲の定義`: Contradiction in the permission model: Section 5.3 states that access is verified based on whether the 'Task ID and target physical address range match' (implying per-task permissions). However, the definition in '物理アクセス許可範囲の定義' and the provided C++ code for `FB_CONF_VMMIO_ALLOWED_ADDRS` define a global static list of allowed ranges without any association to Task IDs.
  - **[WARNING]** `sec:components/tier2_runtime/runtime_vmmio.md#1. コンセプト`: The section mentions that for Tier 2 (Static vMMIO), permission checks are performed during JIT generation and the device key is embedded in native code. This bypasses the runtime 'Permission Table' check described in the definition of {META_RestrictedPhysicalAccess}, creating a divergence in how the restriction is enforced between static and dynamic regions.

### 🟡 WARN: `{GLOBAL_PeriodicTask}`
- **サマリー**: The design sections generally align with the definition of {GLOBAL_PeriodicTask}, but there is a gap between the high-level requirement and the low-level implementation details in the scheduler.
- **詳細項目**:
  - **[WARNING]** `sec:components/tier1_core/os_scheduler.md#4.2 状態遷移図 (SysML SMD: Scheduler 視点)`: The definition of {GLOBAL_PeriodicTask} requires support for periodic execution tasks. While the JIT compiler references this via 'register_periodic_callback', the Scheduler's state transition diagram and detail table only describe event-driven transitions (CSP, Event, Interrupt) and yield/resume. There is no explicit state or transition mechanism defined for how a 'Periodic Task' is triggered or transitioned to READY by the system tick, leaving the actual scheduling mechanism for periodic tasks unspecified.

### 🟡 WARN: `{CleanArchitecture}`
- **サマリー**: The design sections reference {CleanArchitecture} and implement a layered structure, but the BDD (Block Definition Diagram) contains dependency directions that contradict the 'dependency towards the interior' principle defined in the requirements.
- **詳細項目**:
  - **[ERROR]** `sec:architecture/architecture_overview.md#2.2 コンポーネント定義図 (BDD)`: The definition of {CleanArchitecture} explicitly requires restricting dependency directions 'inward' (towards the internal/core logic). However, the BDD shows the 'HAL Layer' and 'Logging' (Subsystem Layer/Infrastructure) providing APIs to or sending events to the 'IPC Router' (Kernel Layer). In a strict Clean Architecture, the inner layers (Kernel/Core) should not depend on or be driven by the outer layers (HAL/Subsystem) in a way that allows the outer layer to define the interface; the dependency should be inverted via interfaces defined in the inner layer.
  - **[WARNING]** `sec:architecture/architecture_overview.md#1. アーキテクチャコンセプト`: The section mentions 'URI-based abstraction' and 'IPC router' as the mechanism for {CleanArchitecture}, but it does not explicitly define which layers constitute the 'Internal' vs 'External' boundaries, leaving the 'inward' direction mentioned in the definition ambiguous.
