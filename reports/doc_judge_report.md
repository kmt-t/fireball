## 1. 検出された矛盾・警告 (Issues Found)

### 🟡 WARN: `{META_ConfigurableSystem}`
- **サマリー**: The referencing sections are largely consistent with {META_ConfigurableSystem}: system parameters are repeatedly described as compile-time fixed via header macros and constexpr constants, and numeric values such as JIT cache size, vMMIO base, and WASM page size agree across sections. However, there are several consistency, completeness, and substantiation gaps: a separate irq_mapping_config is introduced without clarifying that it is compile-time header/constexpr configuration; logging memory pool independence is ambiguous relative to the static RAM accounting model; guest RAM allowed values are ambiguous relative to the 4096-byte default; safety and build-time verification claims lack concrete backing artifacts; and several referenced configuration macros are not defined in the provided configuration details.
- **詳細項目**:
  - **[WARNING]** `sec:components/tier2_runtime/runtime_vmmio.md#4.7 仮想割り込みマッピング vs sec:components/tier1_core/system_config.md#1. コンセプト / sec:components/tier1_core/system_config_details.md#1. 概要`: The virtual interrupt mapping section introduces a separate 'irq_mapping_config' that is managed independently from 'vsoc_config', but it does not state that this configuration is a header macro or constexpr constant fixed at compile time, nor where it is defined. Other sections describe system configuration as header-file macros/constexpr constants, with system_config_details.md stating that the compile-time configuration macros are defined in inc/fireball_config.hxx. This leaves ambiguity about whether irq_mapping_config conforms to {META_ConfigurableSystem} or could be a runtime configuration artifact.
  - **[WARNING]** `sec:components/tier1_core/system_logging.md#6.2 メモリ制約と方策 / #6.3 安全性制約と方策 vs sec:components/tier1_core/system_config.md#静的リソース消費の概算モデル`: The logging section states that logging uses an independent static memory pool and that the log area is isolated by memory partitioning. The static resource consumption model, however, states that FB_CONF_LOG_BUFFER_SIZE is an internal part of the subsystem pool and is not added separately to the total RAM consumption. The relationship between an 'independent static memory pool' and being 'inside the subsystem pool' is not clarified, creating a possible horizontal inconsistency in memory accounting and isolation semantics.
  - **[WARNING]** `sec:components/tier2_runtime/runtime_vsoc.md#vSoC構成（vsoc_config） vs sec:components/tier1_core/system_config_details.md#2.4 vSoC / vMMIO`: The vSoC configuration describes RAM capacity as '64KB or 8KB etc partial page', while FB_CONF_GUEST_RAM_SIZE has a default value of 4096 bytes, i.e. 4KB. If 64KB and 8KB are intended to be the allowed or representative values, the 4KB default is inconsistent. If 4KB is also allowed, the wording should explicitly include it or state that the listed values are examples only.
  - **[WARNING]** `sec:components/tier1_core/system_config.md#6.3 安全性制約と方策`: The section claims that system configuration constants placed as constexpr/const in ROM/Flash .rodata are 'definitely protected' from runtime erroneous writes or tampering. This is a strong safety claim, but no concrete backing artifact is cited, such as MPU configuration, flash write-protection settings, memory attribute definitions, or a verification test. The protection depends on hardware and linker/memory-map behavior that is not substantiated in the text.
  - **[WARNING]** `sec:components/tier1_core/system_config.md#静的リソース消費の概算モデル`: The section states that compile-time macro constants deterministically determine the ROM/RAM footprint and that build-time constraint compliance is verified by static_assert. However, it does not cite the concrete static_assert code, file, or test artifact that performs this verification. As written, the build-time verification claim is under-specified and not directly substantiated by a referenced artifact.
  - **[WARNING]** `sec:components/tier1_core/system_config_details.md#1. 概要 vs sec:components/tier3_jit/jit_compiler.md / sec:components/tier2_runtime/runtime_interpreter.md / sec:components/tier2_runtime/runtime_loader.md / sec:components/tier2_runtime/runtime_vsoc.md`: Several macros referenced as compile-time configuration parameters are not defined in the provided system_config_details.md list, including FB_CONF_JIT_CARD_SHIFT, FB_CONF_JIT_ENTRY_GROUP_SHIFT, FB_CONF_INTERP_STACK_SIZE, FB_CONF_MAX_MODULES, FB_CONF_JIT_ENABLED, and FB_CONF_VSOC_PASSTHROUGH_BASE. This leaves their default values, types, ranges, and derivation incomplete for the {META_ConfigurableSystem} requirement, even though the configuration details section presents itself as the list of compile-time configuration macros.

### 🟡 WARN: `{META_3TierSeparation}`
- **サマリー**: The referencing sections consistently apply the 3-tier labels (Tier 1 primary, Tier 2 decomposed runtime, Tier 3 leaf/platform) and generally align with META_3TierSeparation. No numeric contradictions were found. However, two ambiguities weaken the 3-tier separation: memory management is described as both a Tier 1 COOS component and a Tier 3 platform component without a clear boundary, and the JIT copy-and-patch section ambiguously claims independence from the upper facade's interface while also requiring integration through upper-layer contracts.
- **詳細項目**:
  - **[WARNING]** `sec:components/tier1_core/os_coos.md#2.1 構成要素 and sec:components/tier3_platform/platform_memory.md#1. コンセプト / #2. アーキテクチャ分類`: os_coos.md assigns co_mem, a memory manager, to Tier 1 and describes it as managing task-independent static memory buffer pools/memory partitions. platform_memory.md assigns a memory manager to Tier 3 and describes it as managing the consolidated physical memory pool and independent host/VM heap partitions. The two descriptions overlap in responsibility but place the same named mechanism in different tiers without an explicit boundary, creating a horizontal consistency risk for the 3-tier decomposition.
  - **[WARNING]** `sec:components/tier3_jit/jit_engine_copy_patch.md#6.2 3層分離設計 (3-Tier Separation) とハーネスパターン (Static Dependency Inversion)`: The section states that the Tier 3 leaf is 'completely independent' from the interface defined by the upper facade jit_compiler (Tier 3) and from Tier 1 system configuration. Other sections state that this component is decomposed from jit_compiler and must integrate through upper-layer interfaces/harness contracts. As written, independence from the facade's interface conflicts with encapsulated dependency management; the text should clarify that it is independent of implementation/configuration while still conforming to the facade/harness contract.
