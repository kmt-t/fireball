## 1. 検出された矛盾・警告 (Issues Found)

### 🟡 WARN: `{META_RecoveryStrategy}`
- **サマリー**: The referencing design sections strictly conform to the {META_RecoveryStrategy} definition. All components consistently replace error codes with explicit recovery action enums (ignore, retry, restart, panic). Numeric constraints (3 retry limit, 10ms backoff) are uniformly defined and cross-referenced. Component-specific adaptations (e.g., explicitly excluding 'ignore' for service loading) are documented and do not contradict the core definition. No vertical/horizontal contradictions, arithmetic errors, or unbacked claims were detected. A minor documentation clarification is noted regarding the return type vs. error handling description in the sync_interrupts table.
- **詳細項目**:
  - **[WARNING]** `sec:components/tier2_runtime/runtime_interpreter.md#割り込み同期 (sync_interrupts)`: The function signature table declares a return type of 'void (なし)', but the 'エラー時の挙動' row states that a 'recovery-strategy: ignore' is returned/handled. This creates a minor internal documentation inconsistency. Clarify whether the strategy is applied internally, logged, or if the signature should be updated to return the strategy type.

### 🟡 WARN: `{META_BinarySearch}`
- **サマリー**: The referencing designs consistently implement the {META_BinarySearch} requirement by applying binary search on sorted arrays, correctly enforcing sorted-key invariants and utilizing a 'narrow-then-search' optimization that reduces complexity from O(log N) to O(log n). However, sec:components/tier2_runtime/runtime_loader.md and its test spec introduce an undefined complexity parameter O(k) for RadixBinaryTreeView operations, creating horizontal notation drift and ambiguity against the explicit O(log N) definition. Clarification or alignment of the O(k) notation is required.
- **詳細項目**:
  - **[WARNING]** `sec:components/tier2_runtime/runtime_loader.md (Sections 1, 4.1, lookup-by-file-offset) & sec:components/tier2_runtime/tests/runtime_loader_test_spec.md`: The text repeatedly claims O(k) complexity for RadixBinaryTreeView searches (e.g., 'O(k) 高速検索', 'O(k) / O(log n)'), but the parameter k is never defined or bounded. This creates horizontal inconsistency with Tier 1 and Tier 3 sections that consistently use O(log n) for the narrowed binary search, and drifts from the explicit O(log N) specification in {META_BinarySearch}. If k represents radix depth or key length, it must be explicitly defined and mathematically related to N or n to maintain strict vertical consistency.

### 🟡 WARN: `{GLOBAL_Policy_Memory}`
- **サマリー**: The referencing design sections consistently and rigorously implement the `{GLOBAL_Policy_Memory}` requirement by explicitly prohibiting dynamic heap allocation (`malloc`/`new`) and enforcing static, stack-based, or pool-reuse strategies across all components. All architectural decisions (intrusive lists, non-owning views, fixed-size partitions, explicit rejection of standard containers) align perfectly with the definition. A minor redundancy warning is issued due to duplicated explanatory text regarding the rejection of `std::flat_map`/`std::vector` across multiple component sections.
- **詳細項目**:
  - **[WARNING]** `sec:components/tier1_core/system_containers.md#1. コンセプト & sec:components/tier2_runtime/runtime_vmmio.md#1. コンセプト`: Near-verbatim duplication of the rationale for rejecting `std::flat_map`/`std::vector` based on `{GLOBAL_Policy_Memory}` and `{META_NoStdVector}`. While `runtime_vmmio.md` includes a reference to `system_containers.md`, the explanatory constraint rationale is repeated. Consolidating this constraint justification into a single authoritative section is recommended to prevent future specification drift and maintain a clean source of truth.

### 🟡 WARN: `{JIT_RuntimeAPI_Fallback}`
- **サマリー**: The referencing design sections consistently implement the {JIT_RuntimeAPI_Fallback} requirement through a CPS 4-argument signature, tail-jump delegation, and zero-context-rebuild policy. However, a direct contradiction exists between the instruction set catalog and the JIT compiler delegation policy regarding control flow instructions. Additionally, minor ambiguity exists regarding return-value-based fallback versus the strict CPS tail-jump contract.
- **詳細項目**:
  - **[ERROR]** `sec:specs/wasm_instruction_set.md#3.1 制御フロー命令 (Control Flow) vs sec:components/tier3_jit/jit_compiler.md#コンパイル単位とインタープリタ協調方針`: The instruction set specification table explicitly lists 'JIT Stencil 提供: あり' for control flow instructions (br, br_if, call, etc.). This directly contradicts the JIT compiler policy, which mandates that these exact instructions are 'JIT 側で独自生成せず、インタープリタの命令ハンドラを直接呼び出すか、インタープリタへフォールバックして委譲する' to satisfy {JIT_RuntimeAPI_Fallback}. The catalog must be updated to reflect the fallback-only policy or explicitly marked as unsupported/delegated to prevent implementation drift.
  - **[WARNING]** `sec:components/tier3_jit/jit_compiler.md#4.1 アルゴリズム vs sec:components/tier2_runtime/runtime_interpreter.md#4.1 アルゴリズム`: The JIT algorithm section describes two fallback paths: '末尾ジャンプ（Tail Jump / BX）するか、戻り値 next_ip を返却してインタープリタへ即座にフォールバックする'. The interpreter algorithm section strictly describes a CPS tail-jump model ('レジスタ上の...をそのまま次のオプコードハンドラに渡して末尾ジャンプ（BX）する'). The existence of a return-value-based fallback path is ambiguous under the strict CPS 4-argument signature contract and requires clarification to ensure it does not violate the zero-overhead interop invariant or introduce hidden context reconstruction costs.
