## 1. 検出された矛盾・警告 (Issues Found)

### 🔴 FAIL: `{META_ConfigurableSystem}`
- **サマリー**: Most referencing sections consistently implement META_ConfigurableSystem as compile-time configuration via header macros and constexpr constants. However, one section gives two different values for the same passthrough base address, which is a numeric inconsistency. Additional warnings concern ambiguous use of a 'DYNAMIC' memory region, incomplete macro/constexpr bindings for some configuration parameters, and an unsubstantiated absolute tamper-impossibility claim.
- **詳細項目**:
  - **[ERROR]** `sec:components/tier2_runtime/runtime_vsoc.md#vSoC構成（vsoc_config）`: The passthrough base address is defined as the start of the physical address space used by PASSTHROUGH (FC=15), with the formula physical addr = passthrough_base + offset. The same entry gives 0xF000_0000 and also states 'ARM Cortex-M: 0x4000_0000'. These are different values for the same configured quantity, and no macro, target selection rule, or default is specified. This violates numeric agreement and the requirement that system parameters be statically determined at compile time.
  - **[WARNING]** `sec:components/tier3_platform/platform_hal.md#6.2 メモリ制約と方策`: The section states that HAL buffer count and size are compile-time fixed, but also says the buffers are placed in the vMMIO dynamic area (DYNAMIC). In a specification that repeatedly requires static compile-time memory and avoidance of heap allocation, the term DYNAMIC is ambiguous. It should clarify whether DYNAMIC is a statically allocated region or implies runtime dynamic allocation.
  - **[WARNING]** `sec:components/tier2_runtime/runtime_vmmio.md#6.2 メモリ制約と方策`: This section claims that PTE management realizes a minimal memory footprint according to the number of registered pages. However, sec:components/tier1_core/system_config_details.md#2.4 fixes FB_CONF_VMMIO_MAX_PTES=32 as the static array capacity. If the array capacity is compile-time fixed, the allocated footprint is not determined by the runtime registered page count unless the flat_map_view size/capacity semantics are explicitly specified.
  - **[WARNING]** `sec:components/tier2_runtime/runtime_vmmio.md#4.7 仮想割り込みマッピング`: The section references a separate irq_mapping_config for static 1:1 IRQ mapping but does not specify that this configuration is provided as header macros or constexpr constants, as required by META_ConfigurableSystem.
  - **[WARNING]** `sec:components/tier3_jit/jit_compiler.md#JIT構成（jit_config）`: Several JIT configuration parameters (single bank limit, max registered entries, card boundary shift, instruction boundary shift) are not all bound to explicit header macro or constexpr names. Only FB_CONF_JIT_CACHE_SIZE, FB_CONF_JIT_CARD_SHIFT, and FB_CONF_JIT_ENTRY_GROUP_SHIFT appear in related prose, leaving the compile-time configuration incomplete.
  - **[WARNING]** `sec:components/tier2_runtime/runtime_interpreter.md#インタプリタ構成（interpreter_config）`: The interpreter yield threshold is specified as a 32-bit unsigned compile-time parameter but lacks an explicit macro or constexpr name, while the stack size is bound to FB_CONF_INTERP_STACK_SIZE. This leaves the configuration binding incomplete.
  - **[WARNING]** `sec:components/tier1_core/system_config.md#6.3 安全性制約と方策`: The claim that placing configuration in ROM/Flash makes runtime tampering impossible is an absolute safety assertion. The text does not cite a threat model, access-control mechanism, or verification artifact covering debug access, flash reprogramming, or hardware faults, so the claim is not fully substantiated.

### 🔴 FAIL: `{META_3TierSeparation}`
- **サマリー**: Most referencing sections use the META_3TierSeparation keyword consistently to express a Tier 1 / Tier 2 / Tier 3 decomposition, but there are concrete contradictions in tier assignment and dependency direction. The most serious issue is that jit_compiler is classified as Tier 3 in its own section and in the master physical design, while another section describes it as Tier 2. There is also a conflict between a stated lower-to-upper dependency rule and a Tier 2 component that integrates Tier 3 components. Additional warnings arise from an undefined Tier 0 reference, inconsistent Tier 1 role naming, and unclear responsibility boundaries between COOS and IPC router.
- **詳細項目**:
  - **[ERROR]** `sec:components/tier3_jit/jit_engine_copy_patch.md#6.2 3層分離設計 (3-Tier Separation) vs sec:components/tier3_jit/jit_compiler.md#2. アーキテクチャ分類 and sec:architecture/master_physical_design.md#4. ドキュメント体系上の位置づけ`: jit_engine_copy_patch.md#6.2 states that the upper 'Tier 2 (subsystem domain)' is jit_compiler. However, jit_compiler.md#2 explicitly classifies jit_compiler as 'Tier 3 (詳細リーフコンポーネント: Leaf Component)', and master_physical_design.md#4 places JIT under 'Tier 3 JIT/Platform'. This is a direct contradiction in the tier taxonomy required by META_3TierSeparation.
  - **[ERROR]** `sec:components/tier1_core/system_containers.md#2. アーキテクチャ分類 vs sec:components/tier2_runtime/runtime_vsoc.md#2. アーキテクチャ分類`: system_containers.md#2 states that the dependency direction is always from lower Tier to upper Tier, and that the Tier 1 document does not depend on lower Tier concrete implementations. In contrast, runtime_vsoc.md#2 describes a Tier 2 component that integrates Loader, Interpreter, JIT, vMMIO, and Debugger, including Tier 3 JIT components. This implies an upper Tier 2 component depending on lower Tier 3 components, which conflicts with the stated lower-to-upper dependency rule and weakens the claimed encapsulated dependency management.
  - **[WARNING]** `sec:components/tier1_core/os_coos.md#2. アーキテクチャ分類`: This section introduces 'Tier 0' as the source of system requirements, while the definition and master physical design describe a 3-tier component decomposition using Tier 1, Tier 2, and Tier 3. The text does not clarify whether Tier 0 is part of the 3-tier separation or merely an external requirements layer, creating ambiguity in the tier model.
  - **[WARNING]** `sec:components/tier1_core/os_scheduler.md#2. アーキテクチャ分類 vs sec:components/tier1_core/os_coos.md#2. アーキテクチャ分類, sec:components/tier1_core/system_config.md#2. アーキテクチャ分類, sec:components/tier1_core/system_containers.md#2. アーキテクチャ分類, sec:components/tier1_core/system_logging.md#2. アーキテクチャ分類, sec:components/tier1_interface/ipc_router.md#2. アーキテクチャ分類, sec:components/tier1_interface/system_service.md#2. アーキテクチャ分類`: Tier 1 is labeled inconsistently. os_scheduler.md#2 calls Tier 1 'アーキテクチャドメイン', while the other Tier 1 sections call it '主要システムコンポーネント: Primary Component'. This is a horizontal inconsistency in the tier taxonomy and may obscure whether Tier 1 denotes a domain, a component class, or both.
  - **[WARNING]** `sec:components/tier1_core/os_coos.md#2.1 構成要素 vs sec:components/tier1_interface/ipc_router.md#2. アーキテクチャ分類`: os_coos.md#2.1 assigns COOS a 'co_csp' communication engine for channel-based synchronization and ownership transfer, while ipc_router.md#2 describes the IPC router as the system-wide communication foundation using zero-copy CSP channels and ownership transfer. Both are Tier 1 and both describe CSP-based communication, but the sections do not clarify the boundary, dependency direction, or encapsulation between COOS-internal CSP and system-level IPC routing.
  - **[WARNING]** `sec:components/tier3_platform/platform_memory.md#1. コンセプト`: The section claims that independent heap partitions prevent a memory shortage in one VM from causing other VMs or the host runtime to crash. This is a safety-relevant isolation claim, but no verification artifact, test, formal model, or concrete design evidence is cited. It should be expressed as a design intent or backed by a referenced verification artifact.
